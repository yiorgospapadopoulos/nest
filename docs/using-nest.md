# Using Nest

The full guide to what Nest does, feature by feature. To install it, see the [README](../README.md).

## Mac app

On the Mac a project with no chat open shows the start screen: a question and the composer at the bottom, and beside them what waits on you and the project's recent chats. Approvals and questions are answered in the Needs you card or inline in the chat (a question's last choice is Other, which opens a box to type your own answer); a review waits in the Needs you card and in the bar above the chat's composer, and opens a side-by-side diff and an approve sheet (commit message, push, pull request). A chat's top bar shows its name and status dot on the left, and its worktree or branch, time, pull request, maximize and close on the right; project tabs share one width (about 25 characters, longer names cut). Drag a project tab left or right to reorder the tabs (or use the tab's Move left and Move right accessibility actions); the order is saved by the daemon (`[projects] order` in `settings.toml`), so the iPhone's project list follows it. Settings ends with Restart Nest, which restarts the Nest service and reopens the app; on the iPhone it restarts the service and reloads. Keyboard: Cmd-N new chat, Cmd-W close the focused pane, Cmd-1 to Cmd-9 project tabs, Cmd-Shift-[ and ] previous and next project, Cmd-K search and commands, Cmd-, settings, Cmd-Return send, Esc closes sheets. macOS notifications follow Settings > Notifications (the same kinds and names as on the iPhone) and are skipped for a chat that is on screen; the Dock badge and the project tabs count approvals, failed pull request checks and stuck chats.

To add a project, pick a folder. The root folder of a git repository opens as a git project. Any other folder (outside git, even a new empty one) opens as a plain folder project: chats work in place in it, with no worktrees, branches, reviews, commits or pull requests, and git actions on it answer 409 `not_a_git_repository`. Ask Claude to initialize a repository there (`git init` works like any git command) and the project turns into a normal git project at the end of that turn, or the next time projects are listed.

General holds chats with no project, for a quick question or something to do on the machine itself (disk space, installs, settings). On the Mac it is a tab of its own right after the Pixies tab, before the project tabs, which it never swaps places with; it closes like a project tab (its x or Cmd-W) and is always the first row of the + popover ("Chats with no project"), which opens it again. Cmd-1 selects it while it is open. On the iPhone it is the row under Pixies in the project menu at the top of the Chats tab. Its chats run in a folder Nest owns, `~/Library/Application Support/nest/general/`, made on first use and shared by all of them; Claude Code still loads your own CLAUDE.md, skills, plugins, MCP servers and hooks, and files elsewhere are reached by their full path under the chat's permission mode. Like a plain folder it has no worktrees, branches, reviews, commits or pull requests, even after a `git init` there, and a chat's header shows the machine it runs on instead. It has no settings: chats use the agent defaults. The daemon knows it by the reserved name `general` (`GET /api/repos/general`, not listed by `GET /api/repos`, 409 for edits and removal), which a project cannot take. With no project at all, the app opens on General.

The pointer shows what can be done (a pointing hand on buttons, rows and tabs, an open hand on pane headers that can be dragged). In Connectors (click the account name) the claude.ai connectors and the plugins sit in dropdowns, closed until clicked, with a count and a note when something needs sign-in or failed. Add folder (the + after the project tabs) opens the folder picker as a sheet with New Folder; a plain folder shows an Init chip in place of the branch, which opens a new chat with a prefilled (not sent) request to run `git init`.

Links in chats open only when they are web (`http`, `https`) or `mailto` links; other links stay plain text (the iPhone opens web links only).

Each project has settings (Project settings in the project menu on the Mac, Settings > Projects on the iPhone): where new chats work (Worktree, In place, or the agent default), the gitignored files linked into each worktree, the setup commands run after one is created, and Remove, which forgets the project and deletes its chats with their worktrees and branches (the folder stays). Each change saves only that setting. A link inside `.git` is refused; a link that cannot be made in a new worktree (for example through a folder that leads out of it) is skipped and reported, and the chat goes on.

On the Mac, Settings > Appearance picks light, dark or auto and the accent, which colours primary buttons, selection, focus and your own messages; the Mac has one look. Anything running or loading shows three drifting fireflies in the accent, and a running chat row and the Working line get a soft band of the accent sweeping across them; pixie sprites keep their own hop, and Reduce Motion holds it all still. The iPhone picks its mode and accent in Settings > Appearance. Each project's tab and sidebar show its initials or a pixie sprite in a pixie colour, chosen in Project settings > Icon.

The Mac window is one frosted slab over your desktop: the system's behind-window blur with a dark or light tint, and inside it the tabs, sidebar, right panel and status bar meet edge to edge, split by thin dividers, and the chat, terminal and browser panes fill the workspace edge to edge with faint scanlines, split by 1 pt dividers you drag to resize. With two or more panes open, every pane but the focused one is darker, with its content faded and its title grey; its header, status dot and buttons stay as they are, so a chat that needs you still shows its amber dot (focus dim). A transcript you scrolled up stays where you left it while its pane has the focus; when another pane takes the focus, it jumps back to the latest message and keeps following new ones. The sidebar's rows fill its width: the focused chat's row has a soft fill, chats open in other panes a fainter one, closed chats none; the Pixies list follows the same rule for pixie panes. There is no bar over the project: the project's name at the top of the sidebar opens its menu (new terminal or browser, open in VS Code, Finder or Terminal, copy path, project settings), with its current branch beside it; a thin line under the tabs takes one colour from the chat background (white for a black and white photo, the accent colour without one); the status bar holds the sidebar's squeeze button and Settings on the left, the Workspace / Board / Artifacts switch in the middle, and Terminal and the right panel's squeeze button on the right; each squeeze button is a small triangle pointing where its bar goes. Squeezed, the sidebar is a narrow strip with one status dot per chat (hover for the name) and the right panel a thin line in the accent colour; a click anywhere on either opens it again, and the bars slide and cross-fade between their two forms. With Reduce Transparency on, the window is opaque. Drag the sidebar's right edge to widen or narrow it (double-click resets it); the chats sidebar and the Pixies list share one width on this Mac.

The Mac's chat sidebar is one list, newest activity first, whatever each chat's state; its status dot still shows it. Pinned chats sit above it under a Pinned label (the rest then under Chats); with nothing pinned there are no labels. Archived stays folded at the bottom. In the right panel, Needs you and Goals list one row per item: a status dot, the chat's name (click it to open the chat) over a grey line (what it asks and a short detail, or a goal's "2 of 4" with a thin progress bar), and a chevron on the right that opens the full item in place (Approve, the review, the answer, the checklist). Needs you rows start closed and Goals rows start open. 

A Mac chat's transcript is the web chat in a web view, loaded from the daemon: the sidebar, tabs, right panel, pane header and composer stay native, so scrolling stays smooth with four panes streaming. Moving a pane or switching views keeps its place; closing a pane frees its page. A chat that cannot load, such as with the daemon down or too old to serve the page, says so with Retry and tries again when the connection returns.

Agent messages show as formatted text on every client: tables, block quotes, task lists, rules, strikethrough, nested lists and coloured code for common languages. Code colours are a small built-in tokenizer, the same on both sides; other languages stay plain. Pictures you send show above your message in a fixed box, open larger on a click, and files show as rows you can save; both also appear in queued messages and old chats, with a quiet note for anything deleted in Settings > Storage. On the Mac and Linux, a repo link or a reference such as `web/src/App.tsx:42` in a message opens in the default text app, only when the file is inside the chat's own folder, never run and without jumping to the line; it stays plain text on the iPhone and with a daemon on another machine. On the Mac and Linux, Settings is a panel over the dimmed window: the X, Esc or a click on the dim closes it, and the chats behind it stay as they were.

Dictation uses Apple's on-device `SpeechAnalyzer` (macOS 26 and later), downloading the language model on first use, with project names and coding terms as hints; it falls back to the older speech recognizer when needed.

## Linux desktop app

On Linux, Nest is a desktop app that looks and works like the Mac app: the Pixies and project tabs across the top (the tab strip is the window's title bar, with minimise, maximise and close at its right end), the chat sidebar, a workspace of up to four panes (chat, terminal, browser, run) with focus dim, the right panel with Needs you and Goals, the board, the Pixies tab, Settings (shown inside the main window, with the Mac's pages) and the Ctrl+K palette. Every screen is a desktop component ported from the Mac app (`web/src/desktop/`), with anchored menus and popovers, right-click menus at the pointer, inline rename and details that expand in place; nothing in it comes from the iPhone screens, which an eslint rule enforces. The smallest window is 1000 by 640, as on the Mac. Mac shortcuts use Ctrl for Cmd (Ctrl+N new chat, Ctrl+W close the pane, Ctrl+1 to Ctrl+9 tabs, Ctrl+K, Ctrl+, settings); inside a terminal pane plain Ctrl keys go to the shell, and Ctrl+Shift+C and Ctrl+Shift+V copy and paste. It is a Tauri 2 app (`desktop/`) whose window shows the web UI's desktop layout (`web/desktop.html`, `web/src/desktop/`), bundled in the app, and it talks to the daemon on `127.0.0.1` like the Mac app: it reads this user's device token from the daemon's `token.sock` and sends it as a Bearer token.

- Terminal panes run your login shell in a real pseudo-terminal (portable-pty) drawn by xterm.js. Shell command blocks in chats offer Run in terminal, as on the Mac.
- Links (pull requests, issues, checks, chat links) open in the system browser; pages on this computer's dev servers open in a Nest browser window. Add folder (the + after the tabs) and Save as file use the system's file dialogs.
- On a 2x screen Nest reads GNOME's monitor scale and draws at full sharpness through XWayland; fractional scales look slightly soft there, as for every X11 app on GNOME 46. GTK dialogs draw their text through `GDK_RENDERING=image`, which some virtual and older graphics need, at no measured cost.
- There is no dictation on Linux for now (no mic button).
- Browser panes open the page in a small window of its own for now, because Tauri cannot place several web views inside one window on Linux yet (tauri#10420). Pages there can call nothing in Nest.
- The pixie pill floats at the top centre of the screen, always on top, with the same states as the Mac's notch island. Ubuntu's Wayland session does not let apps keep a window on top or place it, nor take shortcuts while another app is focused, so Nest runs through XWayland by default; Settings > General > Linux > Keep the pixie pill on top turns that off (after a restart, the pill is then an ordinary window).
- The pill never takes the keyboard: clicking it, the tray's Open Nest or a notification gives the focus to Nest's main window.
- The tray icon (AppIndicator, shown by Ubuntu's top bar) has Open Nest, New chat, Settings and Quit. Closing the window keeps Nest in the tray; Ctrl+Alt+N or launching Nest again brings it back (one copy runs at a time).
- Notifications go through the desktop's notification service as Nest, with the Mac's rules; clicking one about a chat opens that chat. While the pill is on, nothing it already shows (a pixie that needs you) is also sent as a system banner; a minimised or hidden Nest counts as not looking.
- Settings > Appearance > Island settings: Show the island and Order (newest or oldest first), kept on this device, as on the Mac.
- Start Nest when I log in (Settings > General > Linux) adds an autostart entry.
- Artifacts open in a frame served from Nest's own `nest-artifact:` address with the artifact rules as a response header, once per view, so the app window keeps its strict rules and artifact pages never reach Nest's commands.

## iPhone access

The iPhone reaches Nest through Tailscale, a free private network between your own devices, never the public internet. The setup guide's Tailscale and iPhone step does it for you: install Tailscale, sign in, then Share with my devices. By hand, run this once on the Mac:

```bash
tailscale serve --bg 8765
```

Tailscale must have Serve and HTTPS certificates enabled for the tailnet (it prints a link the first time). The daemon is then available at `https://<mac-name>.<tailnet>.ts.net/` on devices signed in to the same tailnet; every API call still needs a paired device token. `tailscale serve --https=443 off` turns it off. Requests must be addressed to `127.0.0.1`, `localhost`, `[::1]` or a `*.ts.net` name (a plain host name or bracketed IPv6 address, with an optional numeric port); add other names (or `*.domain` patterns) to `allowed_hosts` under `[server]` in `settings.toml`, else they get 400 "Invalid host header". Wrong pairing codes lock out the address that sent them after 5 tries in 5 minutes (20 in total for all addresses).

To install the phone app: Settings > Devices > Pair a device in the Mac app shows a one-time code; open the tailnet address in Safari on the iPhone, enter the code, then Share > Add to Home Screen.

On the iPhone, Return adds a line and the Send button sends (with a mouse or trackpad attached, Enter sends). When the connection drops, a "Reconnecting..." note shows, and the app reconnects as soon as it is back on screen or online. It sends this device's push subscription to the daemon again on every launch and after pairing. When the Mac cannot answer (asleep, or the daemon stopped), the installed app falls back to its cached shell after 4 seconds, or at once on a server error, and says it cannot reach the Mac. Unsent drafts survive closing the app, text follows the iPhone's text size setting, and error notes stay until dismissed.

The iPhone app follows the Mac's look and wording: flat surfaces split by 1 px lines, the Mac's colours, grey text by default, status as dots and quiet coloured words. Its tabs are **Needs you** (one line per item, the chevron opens it in place; Goals below), **Chats** (a header with the project, its menu to switch project or open Pixies, the current branch and New chat; then Pinned, Chats newest activity first, and Archived) and **Settings** (Configuration, as on the Mac, without the buttons that open files on the Mac). A new chat shows the Mac's start screen fitted to the phone, with the tab bar still under it: the rotating question, what waits on you, the project's open issues and recent chats above it, the composer at the bottom. The composer has the oval field with send inside it, then +, mic and where the chat works on the left, model, thinking and mode on the right; one model menu lists every engine's models and the local models. Long action sheets, such as that menu, scroll inside the screen, so every entry can be reached.

The phone has the Mac's later additions too: Settings > Accounts lists every account of each engine with its windows, a check on the one in use (tap another's check to move it), and ⋯ for Use this account, Rename, Sign out and Remove; Banked resets with Use after a confirmation; and Local models with "Local chats run on" and Add local model (Find on the Mac, with Start for a stopped LM Studio or Ollama, or Enter address). Adding a Claude or Codex account stays on the Mac, where its sign-in happens. Settings > Usage shows the limits of each account in use, and the Chats header shows the first two accounts Top bar shows checks, each as a thin bar and its shortest window ("CL 72% 2h"; the second only when there is room); tapping it opens Usage. From GitHub: the start screen's Open issues with All · Mine (tap to make an issue the first message or open its chat, long-press to start a new one anyway), the `#N` chip and `branch · #N` row, the issue bubble, the PR sheet (tap the PR chip) with "Closes #N on merge" and "Send review comments on their own", Send and Send all to agent on review comments in Needs you, and Approve and push to #N with Approve and commit. A chat on a local model has the Local label, the server-not-running card (Retry, Start the app, Change model) and the weak-at-tools bar ("Don't show again" is kept on the phone). A Needs you item raised inside a pixie call starts its line with that pixie's sprite and name, which the Mac does not show.

## A daemon on another machine

The Mac app can use Nest on another machine on your tailnet instead of the one on this Mac, one at a time. That machine needs Nest installed and shared with your devices through Tailscale, its own copies of the repos and its own engine and `gh` logins: nothing syncs between machines. More detail is in [Working on Nest](development.md#a-daemon-on-another-machine).

- **Pair:** get a code on that machine (Settings > Devices > Pair a device in a Nest app connected to it, or `uv run nestd pair` in a checkout), then on this Mac open Settings > Devices > + Pair a daemon and enter its address (the `tailscale serve` name, for example `mac-mini.tail1a2b.ts.net`; `https://` is assumed, plain `http` only for loopback test daemons), the code and a name for this Mac there. It checks the address first ("Found Nest on <machine>"), then connects.
- **Switch:** the Daemons section at the top of Settings > Devices lists This Mac (always there, the default) and the paired daemons; Connect switches the window, Remove forgets one (its address, its tabs and panes, and its token). Choosing the machine happens only there; the main window shows nothing new. The choice is kept across launches. Each daemon keeps its own open tabs and panes; the look and shortcuts stay this Mac's.
- **Unreachable or refused:** the connection banner names the machine ("Can't reach <machine>. Trying again in <n>s") with Retry and Use This Mac, and a note to check that the machine is awake, its Nest service runs and `tailscale serve` is on. A refused token ("<machine> did not accept this Mac's device token", for example after Revoke there) offers Pair again, with the address filled in.
- **Only on the daemon's own machine:** while connected to another machine, Open in VS Code, Reveal in Finder, Open in Terminal, New terminal, Continue in Claude Code, the Terminal button, Run in terminal, terminal sign-in for connectors, Settings' Open and Reveal buttons and the browser pane's local servers are off (they would act on this Mac); "Copy folder path on <machine>" stays. Accounts shows the command to run on that machine instead of Sign in. Add project takes a typed path on that machine (`~` is its home). Restart Nest restarts that daemon through its API.
- **iPhone:** the PWA belongs to the daemon that serves it, so each machine is its own Home Screen app with its own pairing. The app shows "Connected to <machine>" at the top of Settings and names the machine on the pairing and "Can't reach" screens.

## Notifications

The phone is notified when an agent needs approval, asks a question, has work ready for review, fails or finishes a turn. Tapping a notification opens the inbox (approvals, questions, reviews) or the chat (failures, finished turns).

- **Web push** (free, built in): open the Home Screen app, then Settings > Notifications > Enable notifications. iOS offers push only to the installed app, and asks for permission when you tap the button. Send test checks the whole path. The VAPID key pair is created on first use; its private key lives only in the Keychain (service `nest`, account `webpush-vapid-private`). Revoking a device deletes its subscriptions.
- **Rules** apply to every device and live in `settings.toml`; Settings > Notifications edits them. Editing there rewrites `settings.toml` without its comments.

```toml
[notifications]
vapid_subject = "mailto:you@example.org"   # contact the push services see; Apple rejects localhost
pixie_report_level = "action"              # the least severe pixie report that reaches the phone: info, warn or action

[notifications.kinds]           # true by default, except the two pull request kinds and stuck; usage_limit is a chat paused at the usage limit
finished = false
ci_failed = true                # pull request checks failed (inbox always shows it)
ready_to_merge = true           # checks passed and GitHub can merge (inbox always shows it)

[notifications.quiet_hours]     # optional, the Mac's local time; may wrap past midnight
start = "22:00"
end = "07:00"

[notifications.ntfy]            # optional, off by default
enabled = true
server = "https://ntfy.sh"
topic = "nest-<long random string>"     # 16 to 64 characters
click_base_url = "https://<mac-name>.<tailnet>.ts.net"   # makes a tapped ntfy message open the item
```

- **ntfy** is an optional second channel through the ntfy app. On a public server such as ntfy.sh, anyone who knows a topic can read its messages, so use a long random topic (16 to 64 characters) or a self-hosted server.

## Models, account and agent defaults

The model and thinking selectors list exactly what Claude Code offers: the daemon reads the model list and the signed-in account from Claude Code's startup handshake (a short-lived process with your user settings, no tools and no transcript; no model call, no tokens) on start and every 6 hours, and every agent run refreshes them. They are cached in the database; until Claude Code has answered once, the selectors offer the aliases Default, Opus, Sonnet and Haiku. Thinking shows only the levels the chosen model takes (Extra high and Max included) and is not available for Haiku. Settings > Accounts shows the name and plan; the name is the one Claude Code shows for your account, read from Claude Code's `~/.claude.json` (`oauthAccount.displayName`, else `fullName`; nothing else in that file is used, and it is never changed) when the handshake sends none; the email stays hidden until you tap Show.

Every new chat shows where it will work until its first message, in a selector above the message field in a pane, or in the row under the field on the Mac's empty screen: **Work on <branch>** (the project folder, on the branch it has checked out now) or **New worktree** (its own folder and new branch, started from the folder's current branch, with an optional branch name; a name that exists is refused). Afterwards the chat's sidebar row (beneath the title) and, on the iPhone, its header show the branch icon with the folder's branch or the worktree's name; on the Mac it sits beside the mic under the message field, named in wide panes and as its icon (the name on hover) in narrow ones. A worktree's name is its branch name. To work on several things at once, give each its own worktree; the project folder's branch is switched outside Nest.

A normal chat is not tied to its worktree. Say "delete the worktree" or "make a new worktree" in the chat and it does so when its turn ends, then carries on with its full history, in the project folder or the new worktree. Merging closes nothing and leaves the worktree in place, and deleting a chat keeps its worktrees: you decide when one goes, from any chat in the project. Nest does not check for unmerged work itself; the agent looks at git and tells you. The branch stays unless you ask for it to go too, and then only if git finds it merged; uncommitted changes in a deleted worktree are lost. The left bar shows where the chat works now, and a small count folds out its earlier worktrees, marked deleted or kept. This applies to chats made since late October 2026; older chats, pixie chats, habit runs and chats a pixie started work as before. Any chat follows its agent when the agent enters or leaves a worktree with Claude Code's own tools, so the left bar stays right. A plain `cd` in a shell is not followed. A pixie you call from such a chat can remove its worktree too, so a pixie can finish a job and clean up after it; that waits until the pixie and the chat have finished, and a pixie with read access cannot do it.

New chats use the agent defaults (Settings > Agents > New chats, on the Mac and the iPhone) for anything the composer leaves unset. New chats work in place unless the defaults say Worktree; a repo's `[worktree] default = true` or `false` overrides that for the repo, and a repo file without it follows the default. A thinking level the chosen model does not take is refused (422) when chosen, and dropped when it only comes from the defaults. **Auto** is offered only for models that support it: choosing it for another model is refused (422), a default Auto becomes Ask for a new chat on such a model, and switching an open Auto chat to such a model moves it to Ask before edits (`default`).

Nothing is left to the engine: menus list real models, thinking levels and modes only (no "Default (recommended)", "Default (GPT-...)", "Claude Code default" or "Model default" entries), and Nest passes the model, thinking and mode of every new chat explicitly. When nothing is chosen, a chat gets the default model of the engine you signed in to first (the model that engine marks as its default, by name; Nest keeps which engine it saw signed in first in `engine_sign_ins`), Medium thinking or the level nearest it the model takes, and Ask. The agent defaults also name their engine (`provider`): choosing a Codex model as the default model in Settings > Agents > New chats makes new chats run on Codex.

```toml
[agents]
model = "opus"               # a value from the model list; leave out for Claude Code's default
effort = "high"              # low, medium, high, xhigh or max; leave out for the model's default
permission_mode = "default"  # default, acceptEdits, plan, bypassPermissions or auto; leave out for Claude Code's own defaultMode
default_mode = "in_place"    # or "worktree"
idle_close_minutes = 60      # close an idle agent run after this long; the next message resumes it
```

## What the agent is doing

While a turn runs, the end of the transcript shows a live "Working... 12s" (or "Thinking... 4s" while the agent thinks), timed from the turn's start; when the turn ends, a small line says "Worked for 1m 12s", or "Stopped after 40s" for an interrupted or failed turn (on the Mac it shows only while the pointer is over that reply). Each thinking block is a collapsed "Thought for 8s" row that opens to the thinking (without a chevron when the model left the text out; "Thought" when the time is unknown, as in Claude Code's own transcripts). Tool calls collapse into one line such as "Ran 3 commands, read 2 files", a single call too, unless it is an agent still running or its result has images; the line opens to the calls. Agents read "Running 3 agents, 2 done" then "Ran 3 agents"; the background bar glows while tasks run ("1 running task" for one). With reduced motion the glow is a static highlight.

A turn that ends with an error from Claude (an API error) ends as failed, with "Failed: <reason>" and a "failed" notification; queued messages then wait, as after an interruption.

**At the usage limit.** When Claude Code says the 5-hour or weekly limit was reached, the turn it cut off ends without failing: the chat rests idle, paused until the limit resets, with a "usage_limit" notification instead of "finished". Messages you send meanwhile wait in its queue and nothing starts on its own. 30 seconds after the reset time Claude Code named, the daemon goes on by itself: the queued messages in their order, or with none queued a "Continue where you left off." message, shown as Nest's, so Claude picks up where it stopped. When no reset time was named, it tries again after 30 minutes; a limit that still holds pauses the chat again. Pauses survive a daemon restart: one whose time passed while the daemon was down goes on at once. Resume now goes on at once, Send now on a queued message ends the pause and sends it, and Stop ends the pause without sending anything (the chat shows interrupted and its messages wait); closing, archiving or deleting the chat cancels it too. A chat Claude Code has open elsewhere at the reset is left to it: the pause ends, its messages wait. Habit runs are not paused (they fail, as before), and other chats are not paused with it. On the Mac and the iPhone a paused chat reads "Paused" (not failed), and a notice above the composer says which limit was reached, when it resets with a live countdown, whether the queued messages send then or the chat continues where it left off, and offers Resume now; the continue message shows as a muted Nest row.

Tool calls cut off when a turn ends show as stopped, unless their background task still runs. Thinking streams as Claude writes it, a subagent's text streams under its row, and what your hooks say to you (a `systemMessage`, or why one failed or blocked) shows in the transcript; output a hook gives Claude, such as SessionStart or UserPromptSubmit context, is not shown, as in Claude Code. Claude Code, its MCP servers and hooks run with your login shell's environment (PATH, nvm, pyenv and what your profile exports), read once when the daemon starts its first run; restart the daemon after changing your profile. Claude Code's own notices show as muted lines: "Conversation compacted", "Context cleared" (after `/clear`), a model fallback, the first API retry of a turn, and what a local slash command such as `/cost` or `/context` answers. A permission prompt shows Claude Code's reason when it gives one. The iPhone's background bar counts the current exchange: what started since your latest message, anything still running, and earlier tasks that finish during it. The Mac's bar shows only while something runs: "2 running tasks", opening upwards to the running subagents and background commands, each with how long it has run and Stop; nothing finished is listed. The Mac and the iPhone otherwise follow the same rules.

## Claude Code conveniences

In a chat, typing `/` at the start of the message suggests the session's slash commands and skills, and `@` suggests files of the working directory (inserted as `@path`); Claude Code expands both when the message arrives. A plan Claude finishes in plan mode appears as a plan card with **Approve plan**, continuing in Auto-accept edits, Approve edits manually or Auto (for models that support it), and **Keep planning** (with an optional note). **Always allow** on a permission prompt saves the rule Claude Code suggests (shown on the card, for example `Bash(npm test:*)`) where Claude Code would keep it, such as the repo's `.claude/settings.local.json`; without a suggestion it allows that exact call (the command, the file or the web domain, shown on the card) until the chat's Claude Code run closes. While no turn runs (idle, stopped or failed), in a chat that is not archived, not being published and with no background tasks, **Rewind** on one of your messages works like Claude Code's rewind: restore the code (the files the agent changed since then go back as they were, noted by a muted line), the conversation (that message and everything after it leave the chat, Claude continues from before it, and the message goes back into the composer to edit and send again), or both. Editing a sent message is rewinding the conversation to it. The files preview needs the chat's Claude Code run to be open (send a message first after it closed); with nothing changed, restoring code is disabled with "Nothing to restore". Stop does not cancel a rewind. Messages sent before this feature, in Claude Code or as commands cannot be rewound. **Fork from here** on one of your messages makes a new chat in the same project whose conversation is this one's up to before that message, with the message in its composer; the original stays as it is. A fork of an in-place chat works in the same folder; a fork of a worktree chat gets its own worktree, branched from the original's branch as committed (uncommitted changes stay in the original), when its first message is sent. A quiet "context N%" next to the composer selectors shows how full the context window is, with **Compact** (sends `/compact`). A message sent while Claude works goes into that turn, as in Claude Code: it waits above the composer as a pending message until Claude reads it at its next step (after a tool call) and shows in the transcript where Claude read it; when the turn ends first, it starts the next turn. While pending it has **Send now** (stops the turn and sends it right away) and can be removed (edit it by removing it and sending it again); once Claude has read it, it can no longer be removed. Stop keeps pending messages waiting instead of sending them; they go into the next turn you start. A message that cannot go into the turn (no run open, a new file attachment, while Nest commits or restores) waits and is sent when the turn ends.

The Mac app reports itself as visible (client `mac`) while its window is on screen, shows "as of" times dimmed when older than 10 minutes and a Refresh button in the usage popover (click the usage chip in the tab strip; the chip itself has no refresh button), and the refresh interval under Settings > Usage. Settings > Usage, on the Mac and the iPhone, shows the same limits, periods and breakdown as the usage popover, with the limit checks and warnings under them. Thinking can be changed on open chats; it applies from the next message.

## Search

A new chat has no name at first. A few seconds after your first message it gets the engine's own, live on every device: the title Claude Code generates, or the one in OpenCode's session list. Codex and Gemini give Nest no name, so Nest asks them once, on the same account and their cheapest model, in a call with no tools or history that stays out of the chat. A name you set yourself, a chat named after an issue, pixie chats and habit runs keep their names, and so do chats from before this. If no name comes within about a minute, or the chat fails, it shows a short name cut from your first message, which is also what Needs you cards, notifications and a worktree's branch use from the start.

Search chats, at the top of the iPhone's Chats tab, finds chats across every project by title and by what was said: your messages, Claude's replies, tool calls (name and main argument) and the start of tool output, plus the titles of Claude Code and Codex chats from outside Nest. Words must all match; `"quoted phrases"` match in order and `word*` matches a prefix. Results are grouped by chat, best match first; tapping one opens the chat scrolled to that message, highlighted for a moment. The index lives in the daemon's SQLite database (FTS5) and is filled from stored events; on the first start after the upgrade it indexes the existing history in the background.

In the Mac app, Cmd+K also searches messages across all chats (a "Messages" section) and jumps to the hit with a short highlight.

## Stuck chats

Stuck chats get an amber Stuck badge and a Needs you card with Send a nudge and Interrupt; thresholds live in Settings > Agents > Stuck chats.

Nest flags a running chat as stuck when it waits on a permission prompt, question or plan for too long, runs without any new output, repeats the same tool call with the same input, or runs one turn very long. A stuck chat shows a **Stuck** badge in the chat list and a card in the inbox with the reason, **Interrupt**, and **Send a nudge**, which stops the turn and sends "You seem stuck: <reason>. Step back and try a different approach." The flag clears as soon as the condition ends. Pushing it to the phone is off by default (Settings > Notifications).

```toml
[stuck]
waiting_minutes = 15  # on a prompt; 0 turns a check off
silent_minutes = 10   # no new output
repeated_calls = 4    # the same call more than this many times in a row
turn_minutes = 60     # one turn
```

## Autopilot

The infinity button beside the mic keeps a chat working while nobody watches. The chat runs in Bypass, Nest answers its questions (the recommended option), approves its plans and allows its permissions, and sends a message to go on whenever it stops early. It also goes on after a daemon restart or an engine error, and nudges a chat that looks stuck. The machine stays awake meanwhile; a closed MacBook still sleeps, which only pauses the run.

A run ends when the agent says the task is done, or sooner if you set a time or a weekly usage cap. You can change those during a run. Stop also ends it, and the chat gets its earlier mode back.

A run can use git as it needs, commits and merges included, and can make a worktree and move to it. It merges into the default branch only if the task says so. Pushes and pull requests wait for you unless **Pixies and subagents can push** (Settings > Pixies) is on. Removing worktrees always waits for you. Each decision shows as a line in the chat where it happened, and opens to the options, the one picked and the reason the agent gave. The bar above the composer shows the current step, the time and the number of decisions. A card in the chat says how the run ended and lists what was decided while you were away, with the same lines. It stays where the run ended, like a message, so a chat that ran several times keeps a report for each run. A new chat started on Autopilot gets its own worktree. Habits have the same switch, with their maximum minutes as the time limit.

## Terminal and browser panes

The Mac workspace can hold terminals and browsers next to chats (still up to four panes). New terminal: project menu, palette or Cmd+Shift+T; the Terminal button at the bottom right opens one in the focused chat's folder (its worktree for a worktree chat), or in the project folder when no chat is focused; the sidebar's "Terminal here" opens one in that chat's folder. New browser: project menu, palette or Cmd+Shift+B; the address field accepts a bare port (`3000`), `localhost:3000` or a URL, and "Local servers" lists dev servers listening on this Mac. Shell code blocks in chats offer Copy and **Run in terminal**, which runs the command in a terminal in the chat's folder (its worktree for a worktree chat) after removing control and text-direction characters, and runs nothing when that folder no longer exists; a command of several lines offers Copy only. Closing a project tab keeps its terminals and browsers; removing the project ends them.

## Dev servers

Several chats can run the project's dev server at the same time without fighting over ports. Each folder a chat works in (a worktree, or the project folder for in-place chats) gets its own block of ports, by default 10 from 41000 to 41999 (`[ports] start`, `size` and `blocks` in `settings.toml`). The block is kept for the folder's life and freed when Nest removes the worktree or the project. Its ports reach the setup commands, the run command and the agent as `NEST_PORT` and `NEST_PORT_1` to `NEST_PORT_9`, and the agent's instructions name them, so a server it starts lands in its block.

Add the command to the project's config:

```toml
[run]
command = "npm run dev -- --port $NEST_PORT"
after_setup = false  # true starts it once a new worktree's setup succeeded
```

With a command, a chat's pane header has **Run**. It starts the command in the chat's folder and opens its output next to the chat. While it runs, the header shows the ports it listens on (found from its processes, so a server that ignores `NEST_PORT` still shows). Click a port to open it in a browser pane, or the square to stop it. Chats in the same folder share one run. Closing the output pane leaves the server running. On the iPhone the chat header has Run and Stop, the ports and a sheet with the output; the ports open only on the Mac. Runs stop when the daemon stops.

## Reviewing and publishing

A chat works with git like Claude Code in the terminal, with your own git and `gh` login: ask it to commit and it commits, ask it to push or to open or merge a pull request and it does. Pixie chats, habit runs, chats a pixie started and Autopilot keep that login and may commit, but they can push and open or merge pull requests only while **Pixies and subagents can push** (Settings > Pixies) is on, off by default. While it is off, Nest refuses a typed push or pull request command, stops a scripted `git push` in a pixie's own run, and refuses direct GitHub writes through `gh api`. A script can still get past the block for pull requests and `gh`, and a script's push to a remote with its own push address gets past it too. A normal chat's subagents follow the setting on Claude only, through the command check. On Codex and ACP the setting covers pixies, the chats they start, habit runs and Autopilot, not a normal chat's ordinary subagents. A chat stays a chat: questions and read-only turns bring no review. Only a turn that changed the work (compared with when it started) puts the chat's changes up for review, and that review stays as it is through later turns that change nothing. It waits in the inbox and as a quiet bar above the chat's composer ("3 files changed +40 -12" and **Review**), which opens the diff with one action, Approve. **Approve and open PR** on a worktree chat commits all its work, pushes its branch and opens a pull request; once the pull request is open the button says **Approve and push to #N**, which commits and pushes to the pull request's branch (so work on review comments reaches the pull request), with **Approve and commit** beside it to commit without pushing. On an in-place chat **Approve and commit** commits only the reviewed files to the checked-out branch. Approve and commit never pushes; you push yourself. Approve publishes exactly the review you saw: both clients load the review again for the approval you act on and keep Approve disabled until it shows, approving sends its fingerprint, and the daemon refuses (409 `review_changed`) when the changes or HEAD have changed since. The push sends Nest's commit by SHA to the named branch (`<sha>:refs/heads/<branch>`), after checking that the commit sits on the HEAD that was reviewed, and sets the branch's upstream itself. A checkout on a branch whose name starts with `-`, or that git does not accept as a branch name, is refused (409 `unsafe_branch`). A worktree chat is pushed only from its own branch. The review shows where the work goes ("Pushes to <branch>", or "Commits to <branch>, not pushed"); a push publishes every commit on the branch, Claude's own included. Approving is refused while the agent's background tasks run, when the branch moved since the review was loaded, when the work holds a git repository of its own (shown as "Nested repository, not committed", also for one staged as a submodule that `.gitmodules` does not declare), when git is told to ignore changes to a file to commit (assume-unchanged or skip-worktree), and in a repository that uses git-lfs (Nest runs no hooks, so git-lfs could not upload its files; publish that work from Terminal). The client then reloads the review, keeping the old one on screen meanwhile, and shows why. The review never looks inside submodules (a changed submodule commit still shows), and a text file that attributes or settings mark as binary is shown as text. When origin no longer pushes to the confirmed address (or none was recorded), both clients show where it pushes now and offer **Push there**, which confirms that address and pushes. A message sent while Nest approves or merges waits in the queue and starts afterwards. git and gh commands are stopped after 5 minutes. There is no Reject: to undo work, ask Claude in the chat to change it back (a turn that leaves no changes clears the review), or close or archive the chat. A chat can start in place whatever the checkout holds.

## Pull requests

After Nest opens a pull request it follows it through your `gh` login: every minute, every five minutes once nothing changed for an hour, and no longer once it is merged or closed. The chat header shows a chip with the number and a dot for the checks (amber running, green passed, red failed). When checks fail, the inbox shows the failing check names with **Send to agent**: Nest fetches the end of each failed GitHub Actions job's log with your `gh` login (the last 150 lines, read from a 1 MiB tail, only for jobs of the pull request's own repository, with terminal escapes, control characters, credentials and tokens removed) and sends it into the chat in a code block the log cannot close, marked as untrusted output, so it arrives even when the chat could not read it itself. When the checks pass (or there are none) and GitHub can merge it, a merge approval appears with **Merge (squash)** and **Open on GitHub**; merging also closes the chat and removes its worktree and branch. A chat merges only when you ask it to. Each pull request keeps a short summary from the agent's final summary and the diff stats, without a model call.

Chats with an open PR show `#number` with a checks dot in the pane header and on the Board; click it for the checks list, Refresh and Open on GitHub. Needs you shows a merge card once checks pass (squash by default) and a "Checks failed" card with "Send to agent".

## GitHub issues and review comments

The start screen's right column lists the project's open GitHub issues ("Open issues · N", between Waiting on you and Recent chats; just "Open issues · 0" when there are none), read with your `gh` login, newest updated first, at most 50 read, 5 rows visible and the rest scrolling, cached for a minute. An **All · Mine** switch on the label shows all open issues or only those assigned to you, remembered per project on each Mac; a project's default is `[issues] show = "all"` (or `"mine"`) in its `repos/<name>.toml`. Each row shows the pull requests that will close the issue (`#9 · PR #10`), and the list refreshes every minute while the start screen shows and when you come back to Nest. Clicking an issue that already has an open chat opens that chat (Option-click starts a new one); otherwise it makes the issue the new chat's first message: Nest reads its title, body, labels and comments (bots' comments left out), cleans them like CI logs and sends them in code blocks they cannot close, marked as text written on GitHub. The chat is named after the issue, keeps its number (a `#118` chip left of the PR chip, `branch · #118` on the sidebar row), and a worktree chat's branch is named the way GitHub names one, `118-<title words>`, skipping names already used locally or on GitHub (`-2`, `-3`). The pull request Nest opens for it ends with `Closes #118`, so GitHub closes the issue when you merge; the PR popover says "Closes #118 on merge".

Nest also reads the pull request's review comments with its status (one read-only GraphQL query): unresolved review threads with their file and line, and review summaries that comment or request changes; resolved threads and bots' comments are left out. Comments in the pull request's Conversation tab are not read: ask for changes on the code (Files changed), or tell the agent in the chat. New ones show as a Needs you row ("2 review comments on #131") that opens to each `file:line` and its text with **Send** on each comment, **Send all to agent** and **Open on GitHub**, and as a grey line in the chat. Send to agent sends them into the chat as "Review feedback on #131, sent by Nest", the same way failed checks are sent. While a review thread is unresolved, or a review's comments wait to be sent, Nest offers no merge: the chat has one Needs you row, the review comments, and the merge card returns once every thread is resolved on GitHub and the pull request is ready. The PR popover's "Send review comments on their own" switch (off by default) sends new ones without asking. The one thing Nest writes here: when you press **Approve and push to #N**, it replies "Addressed in <commit> (sent by Nest)" once on each thread whose comments went to the agent, under your `gh` login. It never resolves threads, labels or closes issues; the reviewer checks and resolves. Your own replies on a thread (and Nest's) do not bring it back to Needs you; someone else's new comment does, with the whole conversation. Notices for review comments follow the Approvals notification setting.

## Chats from Claude Code and Codex

Chats you started in Claude Code (Terminal or the Claude desktop app) for a registered project appear in the sidebar (among the chats, newest activity first, on both the Mac and the iPhone) (Codex chats with "Codex" on the second line). Opening one shows its history read-only; **Continue in Nest** takes it over. Automated SDK runs are hidden unless **Settings > General > Show automated chats** is on. Sending is refused while the chat is open in Claude Code.

Nest lists the Claude Code chats of each registered repo (from the terminal, the desktop app or an editor), read from `~/.claude/projects` (or `$CLAUDE_CONFIG_DIR`), never written. Chats a program started through an Agent SDK (entrypoint `sdk-py` and the like, such as automated security reviews) are hidden unless "Show automated chats" is switched on (per device). A chat opens read-only; "Continue in Nest" turns it into a Nest session in the chat's own folder, and the next message resumes it. Sending is refused while the chat is open in Claude Code. New Nest worktrees live in `<repo>/.claude/worktrees/nest-<id>` (`harness-<id>` before the rename; excluded in the repo's `.git/info/exclude`), so `claude --resume` in the project finds Nest chats too. The Claude desktop app only lists chats it started itself.

Archive a Claude Code chat you are done with from its actions (the dots button, long-press or swipe left on iPhone): it moves into the Archived folder with archived Nest chats, and Unarchive brings it back. The archive is Nest's own state (a table in its database), never written to Claude Code, so Claude Code and the Claude app still show the chat. Nest can list more chats than the Claude app: it also finds chats from editors such as the VS Code extension and the terminal, and it cannot see chats you archived in the Claude app, since that state is not in Claude Code's transcripts. Archiving does not stop "Continue in Nest".

Nest also lists the Codex chats of each registered repo that were started outside Nest (the Codex command line, the Codex app or an editor), read through Codex's own app-server (`thread/list`, `thread/turns/list`) on your Codex home (`~/.codex` or `$CODEX_HOME`). A chat belongs to a repo when it ran in the repo folder or in one of the repo's git worktrees (Codex app and Claude Code worktrees included), not in a subfolder. They show beside the Claude Code chats with "Codex" on the row's second line, open read-only, and "Continue in Nest" turns one into a Nest Codex chat in its own folder that resumes the same Codex thread (a chat archived in Codex is unarchived there first, since Codex cannot resume an archived one). Search finds them by title. Chats a program started (`codex exec`, other app-server clients, and Codex chats Nest started but no longer has) are automated and hidden unless "Show automated chats" is on; Codex's sub-agent threads never get a row. Archive and Unarchive use Codex's own archive (`thread/archive`, `thread/unarchive`), so the Codex app and `codex resume` see the change, and a chat archived in Codex shows archived in Nest. Codex is asked again only when its rollout files change, after an archive from Nest, or every 5 minutes. Nest cannot tell whether a Codex chat is open in Codex right now, so nothing stops sending to one that is open there. Nest's own Codex chats are archived in Nest only.

## Codex

A new chat runs on Codex instead of Claude when you pick a Codex model in the model menu. Codex runs as `codex app-server`, from the copy Nest bundles, with your own Codex home (`~/.codex`, or `CODEX_HOME`): your Codex config, MCP servers, skills, AGENTS.md and login apply, as in the terminal. Nest only removes the trust entry Codex writes into its `config.toml` for a worktree when Nest removes that worktree. Codex's models and thinking levels come from Codex (`GET /api/models?provider=codex`); the agent defaults' model and thinking apply only to chats on the defaults' engine, and a chat on the other engine starts on that engine's default model. Permission modes map to Codex's approval policy and sandbox (Ask: `untrusted` and workspace write; Accept edits: the same, with file changes accepted by Nest; Plan: read only; Auto: Codex's own reviewer; Bypass: no sandbox). Codex stays offered when it is not signed in: `GET /api/providers` says so, and starting or messaging a Codex chat answers 409 `codex_not_signed_in` ("Codex isn't signed in. Sign in under Settings > Accounts on the Mac, or run `codex login`."). What only Claude does (rewind, fork, slash commands, taking back a message written into the turn, plan review and `#` memory outside pixie chats) is listed per engine in `unsupported` and refused with 409 `unsupported_feature`. Codex asks its questions with its own `request_user_input` (Nest turns on Codex's experimental API for runs; the short-lived model, login and usage connections stay on the stable one), its plan updates feed the task list and Goals, and Stop on a subagent row interrupts that subagent's thread.

Both engines side by side: on the Mac one model menu lists Claude's and Codex's models, each under the engine's name with its plan or "Not signed in"; choosing a model sets a new chat's engine, and a chat that exists lists only its own engine's models. The usage meter at the top right shows a line per engine signed in (Claude always), for the accounts checked in Settings > Usage > "Top bar shows" (one row per account, dragged or Alt and the arrow keys into any order, kept on that Mac; until you choose, the account in use of each engine; at most the top two lines, the account name shown only when both are one engine's; every checked account in the popover), and the usage popover each engine's windows. Codex's windows come from its ChatGPT plan's rate limits: read during Codex turns, and on the usage refresh cadence by asking a short-lived app-server (`account/rateLimits/read`, no model call). `GET /api/usage/limits?provider=codex` and `POST /api/usage/refresh?provider=codex` serve them (without `provider`, Claude's, unchanged), and `usage.provider_updated` events carry them (`{provider, windows}`; Claude's stay `usage.updated`). Codex's windows are whichever its plan has, each with its length in `minutes` and a `label` from it ("5 hour", "Weekly", "30 day"; the free plan has one 30-day window), shortest first. Usage totals count every engine; `GET /api/usage/period` adds `engines` (`[{provider, tokens, sessions}]`), which the popover's Details show as By engine. `GET /api/providers` also gives Claude's account.

## Local models

A model server on this Mac or the network is added like an account (Settings > Accounts > Local models, or `POST /api/local/models`) and works everywhere a subscription model does: chats, pixies, habits and agent defaults name it `local:<id>`. The chat still runs on Claude Code (the default) or Codex ("Local chats run on", `PUT /api/local/engine`), pointed at the server for that run only: Claude Code through its `--settings` `env` block and the process environment, with a placeholder `ANTHROPIC_AUTH_TOKEN` so a signed-in subscription token never reaches the server; Codex through a `nestlocal` model provider in the thread's config. The user's own settings files are never changed, and Nest works with no Claude or Codex sign in.

| Server | How the engines reach it |
|---|---|
| LM Studio 0.4.1+, Ollama 0.14+, llama.cpp (`llama-server`), Lemonade, vLLM | Codex natively on the OpenAI Responses API; Claude Code through Nest's proxy on the daemon (`/local/<server id>`, 127.0.0.1 only), which passes it to the server's Anthropic Messages API with fixes that keep the server's prompt cache working and its token counts right |
| mlx-lm, other Chat Completions servers | Both through Nest's translator on the daemon (the same `/local/<server id>`), which speaks the missing API to the server's `/v1/chat/completions` |

Requirements: the model must call tools (agents do nothing else), and its context at least 64k tokens (Claude Code's first request alone is about 20 thousand tokens, and with less it compacts the chat after almost every step). Nest rates each model: **Good at tools**, **Weak at tools** (under 14B parameters, or a context under 64k, with how to fix it, such as setting Ollama's context to 64k: Ollama runs every model with 4k unless told otherwise), **no tool use** (refused) or unknown. Find on this Mac (`GET /api/local/find`) looks for servers on ports 1234, 11434, 8080, 9931, 8000 and 5001 and for downloaded models in LM Studio's, Ollama's, Hugging Face's and llama.cpp's folders (`OLLAMA_MODELS`, `HF_HUB_CACHE` and `HF_HOME` respected; a running app's folder is left to its server, and only language models count in the Hugging Face cache); Nest can start LM Studio's server or Ollama (`POST /api/local/start`) and never installs anything. A server's key, if it has one, is kept in the Keychain.

A chat on a local model whose server is not running is refused with 409 `local_server_down` (`app`, `address`, `start`) before the message is taken, and a turn cut off by the server going away ends with the same `code` in its `session.state` event. Images need a model with vision and web search is not available (409 `unsupported_feature`); thinking levels apply only to models that think. Local turns count their tokens per day (`GET /api/local/usage`), never a cost. A server that stops mid-turn fails the turn within seconds (the proxy answers 424, which the engines do not retry). With nothing signed in, new chats, pixies, the agent defaults (not stored then) and artifact page asks use the first local model; `GET /api/setup` says whether this is the first run (nothing signed in, no local model, not yet chosen), and `POST /api/setup/local-only` chooses local models only.

LM Studio loads a model on its first request with the model's own default context (8192 for gpt-oss-20b), which Claude Code's first request does not fit. So when the run of a chat on an LM Studio model opens (after the message is taken and shown), Nest reads `/api/v0/models` and, when the model is not loaded or loaded with less than it needs, loads it with `POST /api/v1/models/load` and 64k of context (or the model's whole context when that is less), showing "Loading <model> in LM Studio" in the chat meanwhile (`session.notice` kind `loading_model`); the run then uses the context it is loaded with. Nest never unloads a model. When LM Studio cannot load it, the turn fails with `code: "local_model_not_loaded"`, `detail`, `app`, `address` and `model` in its `session.state` event, and the message stays in the chat. On any server, a request refused because it does not fit the loaded context comes back to the engine as a 400 (not retried) saying how much context the model has, that an agent needs 64k, and to reload it with more in its app. A model whose size on disk is over 40% of this Mac's memory carries `memory_warning`, one sentence such as "Needs about 12 GB of this Mac's 24 GB: other work may slow down or the Mac may stall." (sizes from LM Studio's `/api/v1/models` and Ollama's `/api/tags`).

## More engines (Agent Client Protocol)

Besides Claude and Codex, chats and pixies can run on other coding agents that speak the Agent Client Protocol (ACP: JSON-RPC over the agent's stdin and stdout), through one generic provider (`nestd/providers/acp*.py`). Each is its own engine with its own sign-in, listed in Settings > Accounts, the one model menu and `GET /api/providers`:

| Engine | How Nest gets it | Sign-in | In Settings |
|---|---|---|---|
| OpenCode | npm `opencode-ai` into `<data folder>/engines/opencode/<version>/` | `opencode auth login` in Terminal (signed in while its `auth.json` holds a provider) | tested |
| Gemini CLI | npm `@google/gemini-cli` into `<data folder>/engines/gemini/<version>/` | a Gemini API key (free from Google AI Studio), kept in the Keychain and passed as `GEMINI_API_KEY`; Google's free "Login with Google" no longer works for personal accounts | tested |
| Cursor agent | your own install of Cursor's CLI (`agent`; Nest cannot fetch it) | `agent login` in Terminal | untested, git warning |

`make install` runs `nestd engines install`, which installs the open engines' listed versions (never globally, needs npm; Engine updates moves them on); a missing one is also installed on first use or with Install in Settings (`POST /api/engines/{name}/install`, progress as `engine.state`). Nest makes each engine ask before shell commands, edits, access outside the chat's folders, web fetches and MCP tools (OpenCode through `OPENCODE_PERMISSION` and, in guarded runs, `OPENCODE_CONFIG_CONTENT`; Gemini through `--approval-mode default` and a Nest system settings file that turns off "always allow") and answers every request itself with the chat's mode, the git guard and a pixie's write root, only ever "allow once" or "reject" (Nest remembers the user's Always allow). Reads and searches inside the chat's folders pass without asking. Cursor agent could not be checked, so Settings warns that Nest cannot block its git commands, and pixies, habits and chats a pixie started refuse it. File writes the engine sends to Nest (`fs/write_text_file`) are checked against a pixie's write root. A chat resumes after a restart with the engine's `session/resume`, or `session/load` with its replay dropped. Models come from the engine (`GET /api/models?provider=opencode`), and OpenCode's models on the user's own servers (LM Studio, Ollama, or a provider in its config with an address on this computer) are marked `local` and listed in a Local section, still run by OpenCode; none of these engines offers a thinking level over ACP. Tokens and context are counted per turn; none reports plan limits, so they get no usage bar. Their chats have slash commands but no rewind, fork, taking back a message, plan review or `#` memory outside pixie chats (`unsupported`). Their plans feed the task list and Goals, they ask questions through Nest's `ask_user` tool (OpenCode waits up to 7 days, Gemini at most 10 minutes), and a pixie's skill list becomes a line in its first message, which the engine may not keep to. Nest's tools (a pixie's memory and habits, artifacts, `call_pixie`) reach the engine as an HTTP MCP server in `session/new`, as for Codex, so pixies run on OpenCode and Gemini and are called with `call_pixie` from any chat. Added accounts get their own folder in `<data folder>/profiles/<engine>/<id>/` (OpenCode: its data and state folders; Gemini: `GEMINI_CLI_HOME`). OpenCode needs `opencode auth login`: it answers ACP on its free models without a login, so Nest counts it signed in only while its own `opencode/auth.json` under the account's data folder (else the user's `XDG_DATA_HOME`, else `~/.local/share`) holds a provider entry, and refuses its chats otherwise. Settings > Accounts lists these engines in one More engines table, a row each with its version, labels, a warning mark for the git warning, its state and one action (Sign in in Terminal, Add key, Install; on the phone, Copy sign-in command); more accounts for them are not offered in Settings. Copilot CLI and Amp were dropped (2026-10-27).

## Engine updates

When an app opens, the daemon asks PyPI and npm whether Claude Code (`claude-agent-sdk`), Codex or the open engines have a newer release. It never checks on a timer. A newer one is installed into a separate environment in `<data folder>/environments/`, leaving the running one untouched, and checked offline with `nestd engines selfcheck`: the daemon starts on throwaway folders and each engine answers its handshake, with no model call. Only then does a Relaunch to update button appear: at the bottom of the left bar above the status bar on the Mac and Linux, covering the chats behind it, a dot on a squeezed bar, and above the tab bar on the iPhone when no chat is open. The chevron beside it shows old and new versions, and the x hides the strip and the dot until the app or page is next opened, kept in memory only. Settings > General always has an Update available row with the versions and the same button while an update is ready, right above Undo update. A new install keeps engine updates back while the setup guide is open and for a day after it is finished, as its engines are only as old as its release; a new Nest is offered at once.

Relaunch to update restarts the daemon on the new environment; if chats are mid-turn it says so first, and they resume as after any restart. The app goes with it: the Mac app quits and reopens once its daemon on this Mac is back, Linux and the iPhone reload the page, and neither shows the connection warning meanwhile. A Mac on a remote daemon stays open and says Relaunching... until it reconnects. If the new daemon does not answer its health check, Nest goes back by itself and says so. The same happens after three failed starts in a row at any later time. Settings > General > Undo update returns to the previous environment the same way, and the update comes straight back as ready to relaunch, with nothing rebuilt or downloaded. One previous environment is kept, and a version that failed and rolled back is not offered again until a newer one is out. A Nest update that failed and rolled back leaves Undo update as it was before it.

`uv.lock` and the repository never change. launchd and systemd keep starting `daemon/.venv`, and `nestd serve` moves into the current environment as it starts. After a deploy that changes the daemon's dependencies, Nest stays on the versions in `uv.lock` until the next app open prepares the update again. To drop out of an environment by hand, delete `environments/state.json` in the data folder and restart.

## Pixies

Pixies are agents you set up once and keep: each has a name, a pixel-art fairy mascot (10 to pick from), a colour (10 presets or your own), a model, a thinking level, a permission mode, its own standing instructions (its soul, `SOUL.md`) and its own memory (`MEMORY.md`, plus notes and an archive of older facts). Open them from the Pixies tab on the Mac (Cmd-0) or, on the iPhone, Pixies in the project menu at the top of the Chats tab. On the Mac the Pixies tab is a workspace like a project's: click a pixie in the list to open its chat as a pane (or focus it), or drag it onto the workspace to split a pane left, right, top or bottom; up to four pixies are open at once, and their panes move, resize, maximize and close like chat panes. The open pixies are remembered and reopen at launch. The Details panel on the right shows the focused pane's pixie; each pane's Details button shows or hides it. With no pixies yet, Reviewer and Tester templates create one with a tap. A new pixie opens its pane and its Details panel on the Mac (the Details tab next to Chat on the iPhone); every change there saves at once. Every pixie can be called and work in every project.

Each pixie has one ongoing chat. Behind it, every run starts a fresh Claude Code session with the pixie's soul, its memory, the names of its notes and the last 12 messages of the chat (memory and messages quoted as data in fenced blocks, "not instructions"), and a turn that leaves the context 60% full makes the next one start fresh, so a long chat never piles up context. The pixie keeps what matters with its memory tools (dated facts, notes, a search across memory, notes and archive) and changes its soul only when you ask. Facts it saves have common credential formats replaced by `[redacted]` (best effort). Reset conversation archives the chat and starts a new one; soul, memory and notes stay. You can edit the soul, memory and notes yourself in the pixie's details; if the pixie changed a file since you opened it, you choose Reload or Keep mine. A change to the soul, memory, name, project access or skills applies from the next message, which starts a fresh run. Its questions and approvals reach the inbox under its name; its notifications on the iPhone are titled with its name and open its page, as do its search results. Hidden pixies show with Show hidden pixies in Settings > Pixies. A pixie's chat is deleted only with the pixie (or archived with Reset conversation), never on its own. Rewind and Fork are not available in a pixie's chat: each run starts fresh, so the earlier runs' checkpoints are gone.

Pixies are powerful by default. A new pixie gets Edit access: it reads and edits its projects' files like any chat, as its permission mode allows. You can set it to Read only or None (only its own folder, `<data dir>/pixies/<id>/workdir`). Those two stop Edit, Write, MultiEdit and NotebookEdit outside that folder in every permission mode, but they do not stop shell commands. Auto mode works only with a model that supports it, as in any chat: a pixie in Auto moved to a model without it goes back to asking (Default). A pixie can use every skill you have or a chosen few, picked from your own skills and those of your enabled plugins. Pixies have no tool rules of their own; your Claude Code permission settings apply as in any chat. A pixie's chat is not reviewed: its edits in a project stay in that checkout uncommitted, and you commit them yourself, or a pixie with the Start level starts reviewed chats instead. It pushes and opens pull requests only while **Pixies and subagents can push** is on.

**Calling pixies and teams.** In any project chat, type `@` to pick a pixie or a team (they come before files in the list), or type `@slug` yourself. The chat's Claude hands that part of the work to the pixie, which runs as a Claude Code helper with its soul, memory, model, thinking and skills; nothing is written into your repo. Every pixie is available in every project, except hidden ones and those with project access None. Inside a call a pixie reads its memory but cannot save to it and cannot use Nest tools; it calls no other pixies (it may use Claude Code's ordinary subagents, such as Explore), except a team's leader, which calls its own team's members. A call shows as its own row with the pixie's mascot and name: click the row to see its steps and answer in place, or the mascot or name to open the pixie. Mentions of pixies and teams in your sent messages show in the pixie's colour (a team in its leader's). Changing a pixie or a team applies from the chat's next message. Not in pixie chats or Claude Code chats synced from the terminal yet. Only solo pixies and whole teams can be called: a pixie in a team is left out of the `@` list, and a message that tags it with `@slug` is refused ("<name> is in @<team>; call the team or a solo copy"); to use the same pixie on its own too, duplicate it and keep the copy outside the team. Tagging a pixie again in the same chat continues the same helper with its earlier work in context, also after Nest reopens the chat's run or restarts; in another chat, or once the pixie's soul, memory or settings changed, it starts fresh.

A team is a named group of pixies with its own `@` handle and always one leader: the first pixie added, until you pick another; when the leader is deleted or leaves, the next member takes over. Each pixie is in one team or none. `@team` hands the request to the leader: it decides which member does which part, calls them itself, waits for their results, puts them together and reports back; the chat then gives the report with a short summary. The chat never calls the members, and while the team works its call shows as the team's row (the team's grid of sprites, "<team> working" in the leader's colour). Tagging the team again in the same chat continues the leader, which continues its own members. Nest holds every agent to this: only a leader calls pixies, only its own members, and members and solo pixies call none. The pixie list shows teams as foldable sections with the leader marked and the team's name in the leader's colour. New team sits next to New pixie; move a pixie with its menu (Move to team) or, on the Mac, by dragging it onto a team. Each pixie row has a menu (⋯ or right-click on the Mac, ⋯ or long press on the iPhone): Open, Details, Duplicate, Move to team, Move Up, Move Down, Hide or Show, Delete. Duplicate makes "<name> 2" with every setting, the soul, memory, notes and archive, and an empty chat. A team's menu has Rename, Change handle, Set leader and Delete team (its pixies stay).

**Each chat's pixies and subagents.** Under each chat in the left sidebar (and in the chat list on the iPhone) a small tree shows two groups; the Mac's right panel has no Agents card, only Needs you and Goals. Pixies: every pixie and team called in that chat, with its sprite and colour and its state; they stay after they finish, since they may be called again. A team shows in its leader's colour with its members under it, the leader marked, each with its own state. Subagents: the chat's ordinary subagents while they run, each with a working indicator, gone when done; one started by another subagent sits one level deeper. Background commands show in the background bar on the iPhone; on the Mac, running subagents and background commands show in a bar above the composer while any runs. While a pixie works its sprite hops and blinks, wherever it shows (still with a plain working dot when Reduce Motion is on), and a team shows as a small grid of its members' sprites, the leader first. Click a subagent to read its whole transcript (prompt, tool calls, results, report), live while it runs; click a pixie to read every call to it in that chat, newest first, continued calls marked; click a team for its members' calls. These views are read-only: ask follow-ups in the chat. A pixie's or team's menu has Send away: it leaves the chat's group and its next call there starts fresh.

**Goals.** On the iPhone, a Goals section under the Needs you list (for the project chosen on the Chats tab) shows, for each chat that is working or has steps left showing, its title (tap to open the chat) and its steps as a live checklist; a working chat without steps yet says "No plan yet", and a finished chat's steps stay until your next message to it.

**Pixies in the notch (Mac).** While the Mac app runs, a black strip around the camera notch shows your pixies at work. The left wing holds the pixies working now (called pixies and teams, calls inside a pixie's own chat and habit runs, on every engine); with none, Nightshade sits there, hopping while an ordinary chat works and falling asleep after 2 minutes with nothing running. The right wing holds pixies that finished, need you, failed or were interrupted, until you look. A pixie that moves between wings flies under the notch. Each side shows up to three pixies and a +N for the rest (orange when a hidden one needs you). A team takes one place with its four-pixie icon. Hovering grows the strip into the list (newest first, five rows, the rest scroll), each row saying what that pixie is doing now. A click opens the chat the pixie works in (with the question in view when it needs you); Nightshade or an empty strip opens Nest, and the +N opens the list. Opening a chat anywhere in Nest counts as seen: a finished pixie leaves, one that needs you calms down until its chat moves on. Ordinary chats never show there. The strip only grows into empty menu bar: with Accessibility allowed (Settings > Appearance > Island settings > Allow) Nest reads where the other apps' menus and status icons are; without it each side shows one pixie with the count on top. It always sits on the main display set in System Settings (the one with the menu bar); when that display has no notch the strip is a pill in the menu bar at the top centre. It stays the same in full-screen apps. Island settings also have Show the island and Order (Newest first or Oldest first, for both sides and the list); Reduce Motion stills the animations.

**What a pixie can do in Nest (autonomy).** Each pixie has an autonomy level in its details. Observe: it lists the chats in every project, reads their history (shortened), sees the inbox and pull request status. Message: it also sends messages into those chats (shown "from <pixie>"), nudges a stuck chat or stops a turn. Start: it also starts chats in any project, always in their own worktree and reviewed as usual, shown "Started by <pixie>", and closes chats it started (an empty worktree is removed; one with work is kept). Answer: it also answers approvals, questions and plans, only in chats it started; your own chats always wait for you. A pixie has your `gh` login and may commit, and it pushes and opens or merges pull requests only while **Pixies and subagents can push** (Settings > Pixies) is on. At no level can it approve reviews, remove projects or change settings, and it never acts on pixie chats. Limits in its details cap the chats it starts: running at once (default 2) and new per day (default 5). A chat it starts cannot use a looser permission mode than the pixie's own. Every change it makes is listed on its Activity page. Chats it starts show as live cards in its chat (and a `pr` card for a pull request it reports); when the chats it started in one turn have all finished, it gets one "Chats finished" message and tells you how they went. From its own chat a pixie can `@`-call every other pixie. The daemon checks all of this in code, never trusting the pixie's instructions.

**Habits and reports.** In a pixie's details, Habits lists its recurring jobs. A habit has a name, what to check, a schedule (every hour at a minute, every day, weekdays or one day a week at a time, in the Mac's local time) and/or triggers (a chat looks stuck, fails, is ready for review, or its pull request checks fail, in any project), and a longest run (default 20 minutes). Habits run whenever the daemon runs, even with the Mac app closed, as long as the Mac is awake; one habit runs at a time; a scheduled run more than 2 hours late is skipped; a triggered habit runs at most once every 5 minutes with every event since its last run. While the 5-hour or weekly Claude usage is at 80 percent or more, scheduled and triggered runs are skipped (shown "Skipped (usage)"); Run now always runs. Each run is a fresh background session with the pixie's soul, memory, tools and autonomy; it speaks only through a report and otherwise ends quiet. History keeps the latest 20 outcomes (reported, quiet, failed, stalled, timed out, skipped) with Open transcript; Run now, Pause, Resume, Edit and Delete are on each habit. A pixie can manage its own habits with its habit tools.

A report has a severity (info, warning, needs action). Every report appears as a card in the pixie's chat; a report from a habit also starts a pixie turn so you can reply in context. Warnings and needs-action reports also appear in the inbox (on the Mac, under Reports at the top of the Pixies list) until read, and needs-action reports count on the Dock badge and the Pixies tab. Opening the pixie marks its reports read. The phone is notified only for needs-action reports by default; Settings > Notifications sets one level for every pixie under the Pixie reports switch (Info, Warnings or Action), and the switch turns them off. A pixie can also offer up to four reply buttons, and suggest a habit you start with one tap.

## Artifacts

Any chat or pixie can save a report, summary, comparison, plan, deck, mockup, chart or diagram as an artifact instead of a long chat message or a file left in the repo. Every agent run gets four in-process tools, served as Nest's own `nest` MCP server next to your own MCP servers: `create_artifact` (title, kind, content; the transcript shows it as `mcp__nest__create_artifact`), `update_artifact` (id, content, optional new title), which saves a new version and keeps the earlier ones, `read_artifact` (id), which returns the latest version's kind, version, author and content so an agent sees your edits before it updates, and `artifact_guide`, which returns Nest's design guidance. They never ask for permission, also in subagents, and the chat's system prompt mentions them and says which kind to pick. An agent updates only artifacts of its own chat, or of its own pixie for a pixie's chat and habit runs; what a subagent or a called pixie saves belongs to the calling chat. A version holds at most 1 MiB of UTF-8 text, and its title at most 200 characters; the tool refuses anything larger with a message the agent sees.

Artifacts are stored in Nest's data folder, never in a repository, so they never dirty a checkout, end up in a commit or vanish with a removed worktree: each version is a file `<data dir>/artifacts/<artifact id>/v<n>.md`, `v<n>.html` or `v<n>.json` (a multi-file page's files in `v<n>/` next to it), and SQLite keeps the history (title, kind, project, chat, pixie, versions with who saved each, and whether you opened the latest version yet). Deleting a chat or a pixie keeps its artifacts, listed under the project as from a deleted chat with the chat's last title; each artifact has its own Delete, which removes its rows and files.

The daemon serves an artifact's content only as JSON, never as a web page. Each version also carries `page`, the whole document a client shows: an HTML artifact as saved (with the bridge's script added, below), or for Markdown a Nest-styled page that keeps the source as plain text and renders it with pinned marked (GFM tables), highlight.js and Mermaid (```` ```mermaid ```` blocks become diagrams). Clients show the page in their own sandbox, in Nest's light or dark theme: on the iPhone an iframe with `sandbox="allow-scripts"` and a content security policy, on the Mac a WKWebView with a non-persistent data store and a content rule list. A page may load scripts only from cdnjs.cloudflare.com, cdn.jsdelivr.net/npm/, unpkg.com, cdn.tailwindcss.com and code.jquery.com, and stylesheets and fonts only from Google Fonts; it cannot fetch or post forms (on the iPhone a frame can still load another site in itself by script). Agents are told these rules (exact library versions, everything else inline or in files, images as data: URIs or files, React with Babel standalone, colors as CSS variables with a dark mode, phone width, plain links). A chat that saves one shows a card in its transcript that opens it, and new artifacts not opened yet are counted for a badge.

There are six kinds. `markdown` and `html` are shown as the agent wrote them. For the four ready-made kinds the agent sends only data and Nest builds the page from its own template (one self-contained document with the bridge's script, Nest's design tokens in light and dark, pinned libraries from the allowed hosts, readable even when they fail to load):

| Kind | Content | Page |
|---|---|---|
| `slides` | Markdown, slides separated by a line that is exactly `---`; 1 to 200 slides, none empty | A 16:9 stage (1280 by 720) scaled to fit, arrow keys, swipe and taps to move, a counter and a progress bar; prints one slide per landscape page |
| `document` | Markdown | A long read with a table of contents from its `##` and `###` headings (a side column on wide screens, a collapsible block on a phone); each `##` section has Edit; prints on A4 |
| `design` | JSON `{intro, layout, screens: [{label, title, description, device, frame, url, html}]}`: `intro` Markdown up to 4,000 characters (`notes` also accepted); `layout` `stack` (default), `grid`, `tabs` or `canvas`; `label` 1 to 3 letters or digits (`variant` also accepted); `title` up to 80; `description` optional Markdown up to 600; `device` `phone`, `tablet`, `desktop` or `square`; `frame` `auto` (default), `browser`, `window`, `phone`, `tablet` or `none`; `url` optional, up to 200, shown in the browser frame; 1 to 24 screens of at most 200 KB each | A presentation for a decision: the intro, then each option with its label, title, description and mockup in its device frame, laid out as a stack, a grid, tabs or a canvas; each screen is static, in its own shadow root, with `:root` read as `:host` |
| `design_system` | JSON `{name, description, colors, typography, spacing, radii, components}`; hex colours, 1 to 200 colours, at most 100 of each other list, components of at most 50 KB | Swatches in light and dark with hex and contrast ratio, the type scale, spacing and radius bars, and components each in a shadow root |

These pages run only Nest's own script: the agent's Markdown, design screens and components are cleaned by an allow-list before they join the page (no scripts, frames, embeds or event handlers, only `http`, `https`, `mailto` and in-page links, images only as `data:`; styles are removed from Markdown, while screens and components keep styles and forms in their shadow roots), and a document saves only within 5 seconds of your click or key press. The daemon checks the data when an agent saves it and answers with the reason (for example `screens[2].device must be phone, tablet or desktop` or `slide 3 is empty`), so the agent can fix it. You can edit a document in the reader: Save sends the whole new Markdown to `POST /api/artifacts/{id}/versions` (`{content, base_version}`), which saves a new version with `author: "user"` (the version line says "Edited by you") and announces it like an agent's save, as `edited`. Only documents can be edited (422 otherwise), and only from the latest version: a save over an older one is refused with 409, and the page asks you to reload. `artifact_guide` gives agents Nest's own guidance on layout and spacing, type, colour with a dark mode and contrast, motion, charts, interactivity and 3D, phone width, and "mockup mode": asked to mock something up, an agent makes a `design` with 2 to 4 clearly different variants labelled A, B, C, real content, and each variant's idea in the notes. Slides and documents have Export PDF: the Mac prints the web view, and on the iPhone (where its WebKit can print the sandboxed frame) the reader sends the page a `{nest: 1, event: "print"}` message, which the bridge's script answers by opening the browser's print.

Pages remember and carry files. What a page stores, with `localStorage` or `window.nest.storage`, is kept per artifact for all its versions, on all your devices, until the artifact is deleted: at most 1,000 keys, 256 KiB a value and 2 MiB a page (UTF-8 bytes of keys and values). A write is applied whole or not at all (413 over a cap), and an open page on another device hears of it at once (`artifact.storage`). The reader has Clear page data. `read_artifact` shows an agent what the page stored, so it can read a tracker's entries. An `html` artifact may come with up to 100 files (16 MiB with the page) in `files` (`{path, content, encoding: utf8|base64}`, relative paths, mime from the extension); a version has only the files sent with it. Nest inlines the ones the page names by a relative path (`<script src>`, `<link rel="stylesheet">`, `<img src>`, `url()` in CSS) and hands all of them to the page for `window.nest.files`; a file is downloaded from the API only as an attachment. `<input type=file>` works, and `window.nest.saveFile` offers a file to save, after asking you.

A page can also read your Claude usage and ask Claude. `window.nest.usage()` returns the same numbers as the Usage page (the five-hour and seven-day limits, today's and this week's tokens and chats) and `window.nest.onUsage` hears each update; nothing else about your account is exposed. `window.nest.ask(prompt, {system})` asks Claude for a small text task through `POST /api/artifacts/{id}/ask` (`{prompt, system?}`, a prompt up to 8,000 characters and a system text up to 4,000): one Agent SDK call on your own Claude Code login, like the usage probe (no tools, settings, MCP servers or thinking, one turn, no transcript, in an empty folder under Nest's data folder), with a short fixed preamble asking for plain text. Each artifact has a daily budget by the daemon's local day, failed calls included (429 with `{detail, resets_at}` when it is used up); one ask runs at a time per artifact (409) and two daemon-wide (a third waits up to 30 seconds, then 409); a call is given up after 60 seconds (502, as is any failure). The answer is `{text, remaining, limit}`, and `GET /api/artifacts/{id}/ask` gives `{used, limit, remaining, resets_at, enabled}` for today. While one runs, readers show "Asking Claude..." from the ephemeral `artifact.ask` event (`{artifact_id, state: started|finished, remaining, limit}`) and the meta line shows "N of L asks today". Their tokens count apart in the usage totals, like the probes' (`asks` in each period), and stay after the artifact is deleted. The defaults, which you can change:

```toml
[artifacts]
ask = true                    # false turns asking off (403)
ask_model = "haiku"
ask_daily_limit = 20          # asks per artifact per local day, 1 to 200
ask_max_output_tokens = 1000  # about how long an answer may be, 100 to 4000
```

A page talks to Nest only through a small bridge. The daemon puts a short script first in every `page` (right after a leading doctype) that defines a frozen `window.nest` (`version: 1`, `openLink(url)`) and sends requests `{nest: 1, id, method, params}`, answered with `{nest: 1, id, ok, result}` or an error `{code, message}` (`unknown_method`, `bad_request`, `too_large`, `rate_limited`, `busy`, `declined`, `unavailable`); on the Mac through a `nest` script message handler with replies, on the iPhone by messages to and from the parent frame. Each app accepts messages only from its own reader's frame, checks the shape, at most 64 KiB per request and 30 requests per 10 seconds per page, and allows only `openLink`. In-page `#anchor` links scroll inside the page (the script handles them itself, without following the link). Any other link click, `window.open` and `nest.openLink` all ask first, "Open link?" with the full URL, and on Open show an `http`, `https` or `mailto` URL in the browser; Cancel answers `declined`, and a second request while the dialog is up answers `busy`. Calls not answered in 120 seconds fail with `unavailable`. The `content` of a version stays exactly what the agent saved.

On the Mac, Artifacts is the third view in the status bar's centred switch (Workspace, Board, Artifacts, also ⌥⌘3 and the palette), with the count of unopened artifacts as a badge. It lists the history newest first (This chat or Whole project; on the Pixies tab, This pixie or All pixies), and the reader steps through versions and has Copy, Save as file and Delete. A pixie's details page lists its newest artifacts. A maximized pane is restored from its own header. On the iPhone, a document button in the chat header and on the pixie page (with the same badge) opens the history and reader in a sheet. Both apps hide a successful save call in the transcript in favour of the card.

## Usage numbers

Claude reports the 5 hour and weekly limits only with a turn, so Nest refreshes them with a tiny probe (Haiku, no tools, settings, MCP servers or thinking; about 400 input tokens) every `usage.refresh_minutes` (default 3) while the Mac app or the iPhone app is on screen, skipping when a Nest turn reported them within the interval. Clients report that they are visible with `POST /api/clients/visibility` on show, on hide and every minute while shown. Probe tokens are listed apart (`probes` in each period), as are the tokens of artifact pages' asks (`asks`), and neither is counted as your sessions. Each window shows "as of HH:MM", dimmed after 10 minutes, and Refresh asks at once.

Tokens are counted for chats and their subagents. A chat's own tokens come from each turn's result; a subagent's come from its replies as they stream, one row per API reply (a reply's several messages count once), including background subagents that finish after the turn. `GET /api/usage/period?unit=day|week|month|year&date=YYYY-MM-DD` returns the day, week (from Monday), month or year holding `date` by the daemon's local calendar: `tokens` (everything), `subagents` (their part), `sessions`, a bar per hour, day or month, `projects` (most tokens first, every pixie chat together as "Pixies") and `probes`. A subagent's output tokens are the engine's early count, slightly low.

```toml
[usage]
refresh_minutes = 3   # 0 turns the automatic refresh off; Refresh still works
warn_percent = 80     # warn once per window period at this percent (50 to 99); 0 turns it off
warn_notify = true    # the warning also reaches the phone (quiet hours apply)
```

When a window first reaches `warn_percent` in its period, the daemon publishes `usage.warning` (`{window, utilization, resets_at}`); clients show a notice, and with `warn_notify` the phone gets a notification and the Mac posts one.

## Settings storage, pixies and accounts

Settings > Storage shows the space Nest's data folder uses as a total, a bar and one line per part (chats, attachments, artifacts, engines, backups, logs and other) with its size and share, lists the largest attachments to delete one by one after a confirmation, and rebuilds the search index. Chats can be archived automatically:

```toml
[storage]
archive_after_days = 30   # leave it out to never archive; 1 to 3650
```

Nest chats not updated for that many days are archived as if you archived them yourself, checked at start, every hour and when the setting changes; pinned chats, chats in a turn or waiting on you, and chats paused at the usage limit are kept. The Claude Code chats Nest lists (automated ones included) are archived the same way after that long without activity, in Nest only (see Claude Code chats below), unless one is open in Claude Code right now. Codex chats from outside Nest are archived the same way after that long, in Codex itself (see Codex chats below). The menu on the Mac and the iPhone offers Never, 1, 2, 3, 7, 30 and 90 days.

What new pixies start with, and the habit rules of every pixie:

```toml
[pixies]
# model = "opus"          # left out: the agent default
autonomy = "observe"      # observe, message, start or answer
project_access = "edit"   # edit, read or none
max_running = 2
max_per_day = 5
habits_paused = false     # true skips scheduled and triggered habit runs; Run now still runs
habit_usage_percent = 80  # scheduled and triggered runs are skipped while usage is this high
```

Accounts shows Claude through Claude Code's own `claude auth` commands (status, Sign in, which opens the browser on the Mac, and Sign out), Codex through Codex's own ChatGPT sign-in (Sign in asks a short-lived `codex app-server` on your Codex home for `account/login/start`, the Mac opens the page it gives in the browser, the row says "Finish in the browser" with a Cancel until Codex reports `account/login/completed`, at most 15 minutes; Sign out is `account/logout`, after a confirmation), and GitHub through your `gh` login; Nest never reads or keeps a password or token. Claude's section of Settings > Configuration finds a standalone Claude Code (on the PATH, `~/.local/bin`, `~/.claude/local`, `/opt/homebrew/bin` or `/usr/local/bin`) and can run Anthropic's official installer when there is none; plugins, marketplaces and skills are managed with `claude plugin ...` commands of the standalone Claude Code, or of the one bundled with the Agent SDK. Running chats pick plugin changes up when their agent process next starts.

Several subscriptions per engine: Settings > Accounts lists each engine's accounts with a check on the one in use (exactly one per engine; only you move it, Nest never switches on its own). Your own `~/.claude` and `~/.codex` stay the first account and run exactly as before. "Add Claude account" and "Add Codex account" sign in a new subscription through the engine's own sign-in in a profile folder Nest owns, `<data folder>/profiles/<engine>/<id>/` (Claude Code keeps that login in its own Keychain item named after the folder; Codex in the folder's `auth.json`). Everything else is shared with the first account by links (CLAUDE.md, settings, skills, plugins, hooks, subagents, commands, chat history; Codex's config.toml, AGENTS.md, skills, rules and sessions, with its databases shared through `CODEX_SQLITE_HOME`), and Claude's MCP servers are copied into the profile's own `.claude.json` before each start, so agents behave the same on every account. The next turn of every chat and pixie runs on the checked account; a turn already running finishes on its own, and a chat open on another account resumes on the new one (verified on this Mac; whether the services accept a chat begun on another account has not been tried). Each row's menu renames the account (shown in Accounts, the usage meter and Top bar shows), signs it out or removes it (added accounts only; its folder goes, the links' targets never). Under Codex, "Banked resets" (with the count when there are any) lists each signed-in Codex account's banked rate limit resets with their expiry, read through Codex's own `account/rateLimits/read`; Use spends one after a confirmation (`account/rateLimitResetCredit/consume`). Claude Code has no banked resets, so Claude has no such menu. Each row shows every limit window in full. Usage: the account in use is refreshed as before; another Claude account keeps its last numbers (a window past its reset time counts as reset) and is asked only on Refresh and once after its sign-in, since asking runs a tiny Haiku turn that starts its five-hour window; Codex accounts are read without a model call.

Configuration shows what the agents read, from the engines' own files, so a terminal `claude` or `codex` sees the same setup. Shared: the instructions (`$CODEX_HOME/AGENTS.md`, which Claude's user CLAUDE.md imports with an `@<absolute path>` line), the skills (Claude's `skills` folder, which Codex sees through the link `$CODEX_HOME/skills/claude`) and the MCP servers (written into `~/.claude.json` and, through Codex's app-server `config/batchWrite`, into Codex's `config.toml`). Each signed-in engine has a section with its "Uses shared" switches, its own items (Claude: plugins, connectors, hooks, subagents, slash commands, permission rules, settings file; Codex: plugins and marketplaces, hooks, rules, `config.toml`) and "Copy <engine>'s setup to Shared" with Undo. Every change is backed up first under `config-backups/` in the data folder (last 50 kept). A project's settings page shows the repo's AGENTS.md and CLAUDE.md, project skills and `.mcp.json` servers (Claude only).

## Features

Settings > Features (right after Configuration, on the Mac and the iPhone) lists what makes Nest different, grouped by area: Getting around, Chats, Worktrees and git, Pixies, Artifacts, and Engines and devices. Each group is a row with its count that opens to its features, each with one or two plain sentences and where to find it. The list comes from `daemon/src/nestd/features/catalog.toml`, which every block that adds or changes a user-visible feature updates. A feature added or changed recently shows **New** on each device until you close Settings after that device first showed it; until then the Features tab shows a dot and the count, and each group with something new a dot. On a device's first visit, features dated that day or the day before count as new. Each device remembers which groups you opened.

## Performance

Settings > Performance (after Usage, on the Mac and the iPhone) measures Nest on this Mac. Run all measures every section, each section's Run only that one; the page shows the latest result of each section, every number with its change against the run before (an arrow and a percent, or tokens for token counts), bars for the previous run and this one, and at the bottom what changed most with its likely cause (a new Nest version, an MCP server added or removed, a CLAUDE.md that grew, more skills). Top cards: a new chat's context, cache hit rate, first reply and how fast the biggest chat opens. Main sections: Context cost, Turn speed and cache, Load speed, Waiting on you and Activity; Advanced (closed each time the page opens): Pixies, Subagents, Reliability, Engines, Mac app, Daemon, Worktrees and Quality gates.

Two sections spend a little usage: Context cost runs one tiny Claude turn on Haiku in General, set up exactly as a new chat (Nest's instructions and tools, your settings, plugins, skills and MCP servers), and reads Claude Code's own context breakdown, which also counts the MCP tools tool search defers; Nest's own parts are estimated from their text. Engines runs "Reply with the word ok" on each signed-in engine on its smallest model, outside any chat and without leaving a chat in Claude Code's or Codex's own history. Everything else is read from Nest's database and the daemon: turn times from stored events, tokens and cache from per-turn usage (the last 7 or 30 days), load times from in-process calls to the same routes the apps use with their sizes (the slow phone network is an estimate at 1.6 Mbit/s and four 300 ms round trips), route times since the daemon started, and the daemon's start time on each start. The Mac app section is measured by the Mac app itself (laying out and scrolling the biggest chat offscreen, memory before and after), so the iPhone shows its latest result without a Run button. `make check` records each part's time to `gate-times.jsonl` in Nest's data folder when it passes (`nestd gates record`), shown under Quality gates.

Runs are kept in the database (`perf_runs`) forever; Clear old runs keeps each section's two latest. Nothing leaves the Mac. API: `GET /api/perf`, `POST /api/perf/runs` (`{"sections": [...]}`, empty for all; 409 while a run is going), `POST /api/perf/client` (the Mac's own section), `POST /api/perf/clear`; a `perf.run` event tells open pages to refresh.
