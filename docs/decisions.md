# Decisions

Why Nest (called harness until D080) is built the way it is. Newest entries at the bottom. Superseded decisions stay, marked as such; earlier entries keep the old name.

## D001 (2026-10-06): Orchestrator around the official Claude Code engine

- **Question:** Build a custom agent loop, or orchestrate the official one?
- **Decision:** harness is the app around the agent (sessions, UI, approvals, git, config). The agent loop stays Claude Code's, so agents behave exactly like Claude Code with the user's own setup.
- **Rationale:** Keeps agent quality identical, reuses CLAUDE.md, skills, plugins, MCP and hooks, and is the only way to run on a personal subscription for free. A custom loop would need billed API calls.
- **Scope:** Agent behavior is customized only through supported SDK options (MCP tools, subagents, system prompt appends, hooks, per-repo instructions).

## D002 (2026-10-06): Run everything on the MacBook Air

- **Question:** Which machine hosts the daemon and agents?
- **Decision:** The MacBook Air itself, left on.
- **Rationale:** No extra hardware or cost; same environment as the user's current Claude Code setup.
- **Consequence:** Agents pause while the Mac sleeps. Accepted by the user. This supersedes the original note that work should continue with the laptop closed.

## D003 (2026-10-06): Drive agents through the Claude Agent SDK (Python)

- **Options:** A) Agent SDK; B) interactive CLI in tmux with screen scraping; C) detached headless `claude -p` stream-json processes.
- **Decision:** A.
- **Rationale:** Structured events, permission prompts via callback, per-session model, effort, permission mode and attachments as options, loads user settings. B is fragile; C rebuilds what the SDK provides.
- **Consequence:** A daemon restart interrupts an in-flight turn; the session is resumable. The daemon is separate from the Mac app so app restarts never affect agents.
- **Follow-up:** B01 spike verifies settings, plugin and hook loading, resume, the permission callback and claude.ai connectors before building on them.

## D004 (2026-10-06): The daemon performs all git and GitHub actions after approval

- **Options:** A) daemon commits, pushes, opens PRs and merges after UI approval; B) agents commit, only push and PR are approved; C) intercept agent git commands via the permission callback.
- **Decision:** A.
- **Rationale:** Deterministic, testable git logic; the agent can never push regardless of permission mode; review happens before anything is committed. The user's global Claude settings only deny `git push`, so harness enforces its own per-session block of `git commit`, `git push`, `gh pr create` and `gh pr merge`.
- **Flow:** Approve (commit, push, PR), reject, or send feedback into the same agent session. Merge is a separate approval once CI is green.

## D005 (2026-10-06): Existing checkouts, worktree per task by default

- **Options:** A) register existing local checkouts, worktree or in place per task; B) daemon-owned clones.
- **Decision:** A, with worktree as the default for new repos.
- **Rationale:** No duplicate clones to sync; worktrees isolate parallel agents and the user's own edits, as in other parallel-agent tools.
- **Details:** Per-repo TOML in `~/.config/harness/repos/` with `link` (gitignored files such as `.env`, symlinked from the main checkout, never copied) and `setup` (commands run after worktree creation). On repo registration the app suggests link candidates. Worktrees are removed after merge or discard. In-place tasks warn on a dirty checkout.
- **Superseded in part:** new chats work in place by default (D038). Link suggestions exist in the API (`GET /api/repos/{name}/link-suggestions`), but no client offers them yet.

## D006 (2026-10-06): Free only; native SwiftUI Mac app plus iPhone PWA

- **Options:** A) one SwiftUI app for Mac and iPhone; B) SwiftUI Mac app plus PWA on iPhone; C) wrapped web UI on the Mac.
- **Decision:** B.
- **Rationale:** The user wants a real Mac app and wants the project to be free. A native iPhone app without the paid Apple Developer Program expires every 7 days and cannot receive Apple push. C was excluded because the Mac client must not be a web app.
- **Consequences:** Two client codebases. iPhone notifications use web push (requires the PWA on the Home Screen) with ntfy as a fallback. iPhone voice input uses keyboard dictation.

## D007 (2026-10-06): React, TypeScript and Vite for the PWA

- **Options:** A) React + TypeScript + Vite; B) Svelte + TypeScript; C) server-rendered HTMX.
- **Decision:** A.
- **Rationale:** Strongest agent fluency and mature libraries for diffs, command palette, long streaming lists and PWA support. C is a poor fit for live streaming and is not a typed frontend.
- **Related:** Design tokens live in one file (`design/tokens.toml`) and generate CSS variables and Swift constants so both clients share one look.

## D008 (2026-10-06): Tailscale plus per-device pairing

- **Options:** A) per-device pairing tokens; B) passkeys with Face ID; C) password and session.
- **Decision:** A. Passkeys recorded as a later improvement.
- **Details:** The daemon listens only on localhost and the Tailscale interface. The Mac app reads its token from the Keychain. The iPhone pairs once with a short-lived one-time code shown in the Mac app. Devices are individually revocable. Secrets live in the macOS Keychain; GitHub uses the existing `gh` login.
- **Superseded in part:** the binding detail, by D014; how the Mac app gets its token, by D075 (it asks the running daemon over a private socket; the token stays in the Keychain).

## D009 (2026-10-06): Coverage scope

- **Decision:** 100% of logic. Daemon: line and branch, excluding only the entry point. PWA: lines, branches, functions and statements including components, excluding only the bootstrap file and generated tokens. Swift: 100% of the `HarnessKit` package; SwiftUI views verified by screenshots and interactive checks.
- **Rationale:** Line-level tests of SwiftUI views are brittle and prove little; keeping logic out of views keeps the guarantee meaningful.

## D010 (2026-10-06): Single repository, config and data locations

- **Decision:** One repository with `daemon/`, `web/`, `apple/`, `design/` and `docs/`. User config in `~/.config/harness/` (TOML). Data in `~/Library/Application Support/harness/`. Modules (providers, integrations, notification channels) are internal and toggled in config; no third-party plugin loading.
- **Rationale:** Simplest layout that keeps the pieces separate; config stays readable and versionable by the user; YAGNI on dynamic plugins.
- **Note (2026-10-08):** the module registry holds no modules yet; notification channels are switched on and off in `[notifications]`.

## D011 (2026-10-06): Development workflow for this project

- **Decision:** Agents: Opus 5.5 medium for implementation, Opus 5.5 high for difficult work, review and coordination. Blocks are large; after the user accepts a block, the coordinator commits it locally as several small conventional commits. The user pushes. Planning files (`plans/`, `AGENTS.md`, `CLAUDE.md`) are never committed; this decisions log and the README are.

## D012 (2026-10-06): Agent SDK spike findings (B01)

Spike run with `claude-agent-sdk` 0.2.163 and Claude Code 2.1.285, mostly on `claude-haiku-4-5` to keep subscription use small.

- **Auth:** works through the existing local Claude Code login (`apiKeySource: none`); no API key or `setup-token` needed.
- **User setup:** with `setting_sources=["user", "project", "local"]` the session loads all enabled plugins, 83 skills, user hooks, MCP servers including claude.ai connectors (Gmail, Calendar, Drive and others connect), and the project CLAUDE.md.
- **Permissions:** `can_use_tool` can hold a prompt open (tested 20 s per prompt) and resolve allow or deny from outside; the deny message reaches the agent.
- **Resume:** resuming by session id works after a clean close and after a hard kill of the CLI process mid-turn.
- **Controls:** `set_model` and `set_permission_mode` work mid-session; `effort` is an option; image content blocks in streamed user messages work; `include_partial_messages` yields token-level stream events.
- **Usage:** every turn emits a `RateLimitEvent` with five-hour and seven-day utilization and reset times. The usage meter (B15) is feasible from this data.
- **User hooks:** the user's iTerm `cc-status` hooks fire without a terminal and cause no errors.
- **Git blocking:** permission rules alone (`disallowed_tools` with `Bash(git commit:*)` etc.) are bypassable: `sh -c 'git commit ...'` and `git -c k=v commit ...` succeeded. See D013.

## D013 (2026-10-06): Layered enforcement of the agent git block

- **Context:** D004 requires that agents never commit, push or open PRs. D012 showed permission rules alone are insufficient.
- **Decision:** Four layers in every agent session:
  1. `disallowed_tools` rules for `git commit`, `git push`, `gh pr create`, `gh pr merge`.
  2. A PreToolUse hook (SDK callback) that denies any Bash command matching git commit or push or gh pr create or merge anywhere in the command, including wrappers and git options. Verified in the spike to block all tested variants.
  3. Agent processes get an environment without git credential helpers or a GitHub token, so a push that slips through cannot authenticate.
  4. After each turn the daemon audits the repository refs; any commit or ref change it did not make raises an alert event and blocks approval until the user decides.
- **Rationale:** No single layer is complete (an agent could write a script that runs git), but together they make an accidental or casual bypass detectable and a push practically impossible. The threat model is a cooperative agent, not an adversary.
- **Refined by:** D049 (layers 1 and 2: shell-aware matching, every tool), D050 (the approved commit and push) and D053 (safe branch names and a fresh ref audit before publishing). Layer 4 runs hardened git since D064.

## D014 (2026-10-06): Daemon binds to localhost only; Tailscale reaches it via `tailscale serve`

- **Supersedes:** the binding detail in D008 (localhost plus the Tailscale interface).
- **Decision:** The daemon listens only on `127.0.0.1`. Remote devices reach it through `tailscale serve`, which terminates HTTPS on the tailnet name and proxies to localhost.
- **Rationale:** One listening address, no interface detection, HTTPS for free (needed for web push and secure cookies), and nothing reachable from the local Wi-Fi. Device tokens still guard every request.

## D015 (2026-10-06): Daemon platform libraries

- **Decision:** FastAPI with uvicorn for HTTP and websockets; pydantic for config and API models; `aiosqlite` with plain SQL migrations tracked by `PRAGMA user_version`; `keyring` for the macOS Keychain; `tomli-w` to write TOML (reading uses stdlib `tomllib`); `httpx` for tests.
- **Rationale:** Small, widely used, typed libraries; no ORM, since the schema is small and plain SQL is the most readable option.

## D016 (2026-10-06): Git guard matching and the SSH push gap

- **Decision:** The PreToolUse guard matches `commit` and `push` only in git's subcommand position (after global options such as `-C`, `-c`, `--git-dir`), anywhere in a command line, plus `gh pr create|merge`. This avoids blocking harmless commands such as `git log --grep commit` or `git stash push`.
- **Accepted false positives:** text that merely contains a git command (`echo "git commit"`), `git commit-tree`.
- **Known misses:** git aliases and commands assembled from variables or scripts; pushes over SSH remotes, since removing credential helpers does not affect ssh-agent keys and blocking SSH would also break `git fetch`.
- **Mitigation:** the layer 4 ref audit (D013) reports any ref change, including remote-tracking refs updated by a push, and blocks approval until the user decides.
- **Refined by:** D049 (the matching rules).

## D017 (2026-10-06): Agent task list and question tool

- **Findings (live, Claude Code 2.1.285):** the CLI has no TodoWrite; agents track work with `TaskCreate`, `TaskUpdate`, `TaskList`, `TaskGet`. Subagents are started with the `Agent` tool (input `subagent_type`, `description`, `prompt`); their messages carry `parent_tool_use_id` pointing at that call. `TaskCreate` input has `subject`, `description`, `activeForm`; its result text is `Task #<id> created successfully: <subject>`; `TaskUpdate` input has `taskId` and `status` (`in_progress`, `completed`). `AskUserQuestion` is available only when a permission callback is set; its input carries questions with options, and Claude marks its preferred option with "(Recommended)" in the label. Answers are returned through `updated_input` with an `answers` map.
- **Decision:** the "Current work" panel is fed from the agent's task list tool calls; the "Agents" panel from `Agent` calls and subagent messages; questions join the approval queue.

## D018 (2026-10-06): Questions must reach the user in every permission mode

- **Context:** `can_use_tool` is not invoked in `bypassPermissions` or for auto-allowed tools, so a question could be skipped silently.
- **Decision:** intercept `AskUserQuestion` with a PreToolUse hook (which runs in every mode), hold it in the approval queue, and return the user's answers as updated input. Verify live in B05.

## D019 (2026-10-06): Approval queue and review rules (B05)

- **One path:** permissions and questions are resolved through `/api/approvals`; reviews through the session's approve, reject and feedback actions. The earlier per-session permission endpoint was removed.
- **Always allow:** allows that tool by name for the rest of the session (persisted). Allowing Bash allows all Bash; the git guard hook still applies. Superseded in part by D061: when Claude Code suggests rules, Always allow applies those; allowing by name is the fallback.
- **Reviews:** created when a turn ends idle with changes since the last approved commit; at most one pending per session; a new message supersedes it.
- **Git failures:** a failed git or gh step returns 502 with the step and stderr; retries skip steps already done.
- **Tracking:** task list and agents are rebuilt lazily from persisted events after a restart.
- **Questions:** the PreToolUse hook waits up to 7 days, because the SDK default of 60 s would abandon a question.
- **Live evidence:** see B05 in the plan (real PR on a private sandbox repo, questions in two permission modes).

## D022 (2026-10-06): Chat management, titles, usage and local apps (B20)

- **Titles:** sessions created without a title get a short one from the prompt (first sentence, leading filler words removed, at most 48 characters at a word boundary); branch slugs use it (at most 40 characters plus a short hex suffix).
- **Purge:** deleting with purge removes the run, worktree, branch, attachments, approvals, events and the session row. Token usage rows are kept, because those tokens were really spent and monthly totals should not drop.
- **Usage:** every turn's token counts (input, output, cache creation, cache read) are stored; "total" is the sum of all four. The latest 5 hour and weekly limits are persisted.
- **Connectors:** reported from Claude Code itself; harness shows status and points to claude.ai or Claude Code for sign-in, since it cannot authenticate connectors on the user's behalf.
- **Continue in Claude Code:** opens a generated `.command` launcher in Terminal (`claude --resume <id>` in the session folder), which needs no Automation permission. A warning is returned while harness still holds the session's run.

## D023 (2026-10-06): Design token pipeline (B06)

- **Decision:** `design/tokens.toml` is the single source for colors (light and dark), status colors, the six accents, glass, wallpapers, radii, spacing, typography and motion. `harness design generate` writes `web/src/generated/tokens.css` and `apple/Sources/HarnessKit/Generated/DesignTokens.swift` (path updated by D024); both generated files are committed, and a test fails the gates when they drift from the TOML.

## D024 (2026-10-06): Mac app built as a Swift package

- **Decision:** `apple/` holds one Swift package with a `HarnessKit` library (all logic, 100% coverage) and a `HarnessApp` executable (SwiftUI views only). A `make app` script builds it and assembles an ad-hoc signed `Harness.app` bundle with its Info.plist. No `.xcodeproj`.
- **Rationale:** everything stays plain, reviewable text and builds from the command line with the installed toolchain (Xcode 27, Swift 6.4, macOS 27 SDK); Xcode can still open `Package.swift` for previews and debugging. No extra tools such as XcodeGen.
- **Gates:** `swift format lint --strict`, Swift 6 language mode with strict concurrency, `swift test --enable-code-coverage` with a 100% check on `HarnessKit` sources.
- **Superseded in part:** "views only" no longer holds exactly. The app target also has thin glue (the shell controller that connects, sends, attaches, runs terminal commands and handles drags), outside the coverage gate. B32 moved the logic its fixes touched into HarnessKit (D060).

## D025 (2026-10-06): PWA serving and websocket Origin rule (B10)

- **Serving:** the daemon serves the built PWA (`web/dist`, or `HARNESS_WEB_DIST`) at `/` without auth, since the shell holds no data; `/api` keeps priority; app routes fall back to `index.html`; hashed assets are cached long, everything else `no-cache`.
- **Origin:** browser websocket connections must come from the request's own host or from `server.allowed_origins`; others are closed with 4403. Native clients send no Origin and are unaffected. Verified over `tailscale serve`, which passes the Host header through.
- **Pairing cookie:** secure and same-site strict, so pairing works over HTTPS (Tailscale) or localhost only.
- **Client choices:** model selectors use Claude Code aliases (`opus`, `sonnet`, `haiku`); task-list tool calls are hidden from transcripts because Goals shows them.
- **Superseded in part:** model selectors list Claude Code's own models (D038).
- **Refined by:** D064 (a Host header check besides the Origin rule).

## D026 (2026-10-06): Notification delivery (B11)

- **Always on:** delivery is part of the daemon, not an optional module: it follows the event bus from startup (replaying from the last event id it saw, so nothing published during startup or after falling behind is lost) and sends each `notify` event in a background task. Web push goes to every subscription of a non-revoked device; ntfy only when enabled.
- **Web push:** `pywebpush` encrypts the payload (aes128gcm); the VAPID token is signed per request (one hour) with `py-vapid`; requests go out through `httpx` (now a runtime dependency) so sends are async and tests use a mock transport. TTL one day; urgency high for approvals and questions. 404 and 410 delete the subscription; other failures increment its `failures` count (reset by a success). Only the endpoint host is logged, never its path, keys or the VAPID key.
- **VAPID key:** P-256, created on first use, stored as PKCS#8 PEM in the Keychain (`webpush-vapid-private`); the public key is derived. An unreadable stored key is replaced with a warning, which invalidates existing subscriptions. `vapid_subject` defaults to `mailto:harness@example.com` because Apple rejects localhost subjects; it is configurable.
- **Payload and links:** `{title, body, url, tag}`; approvals, questions and reviews open `/inbox`, failures and finished turns open `/chat/<session id>`; the tag groups notifications by session.
- **Rules:** `[notifications]` in `settings.toml` (kinds, optional quiet hours in the Mac's local time, optional ntfy). `PUT /api/notifications/settings` replaces the section, re-reads the file so other edits survive, validates the whole file and writes atomically; comments are lost. A broken file is reported (409), never overwritten. Quiet hours suppress notifications entirely; the inbox still shows everything. The test notification ignores rules.
- **ntfy:** published as JSON to the server root (headers cannot carry non-ASCII titles), with priority 4 for approvals and questions, a tag with the kind and a click URL when `click_base_url` is set.
- **PWA:** the app keeps its route in the address (`/inbox`, `/projects`, `/account`, `/chat/<id>`). A tapped notification focuses an open window and posts it the path, or opens a new window there. The service worker is a classic script, so it shares no module with the app (a test enforces it). Subscribing asks for permission first, inside the tap, as iOS requires; a subscription made with another daemon key is replaced.


## D027 (2026-10-06): Removing a project

- Removing a project unregisters it and can purge its chats; the repo folder is never touched; purge tolerates a missing repo folder.
- `DELETE /api/repos/{name}` answers 409 while the repo still has sessions (archived ones included), unless `purge_sessions=true` purges them first through the session purge path. It then deletes `repos/<name>.toml` and publishes `repo.removed` (global, payload `{name}`).
- When the repo folder is gone, worktree removal skips every git call (worktree remove, prune, branch delete) and only deletes the leftover worktree directory inside the harness worktrees dir; the rows are deleted as usual.
- Commands run in a missing working directory raise `CommandError`/`GitError` with a clear message instead of a bare `OSError`. New sessions in a repo whose folder is gone, link suggestions and approvals in a missing working directory answer 409; a turn in a missing folder fails the session.

## D028 (2026-10-06): Claude Code chat sync (B21)

- **Import source:** Claude Code's own transcripts, `<claude dir>/projects/<encoded folder>/<session id>.jsonl`, where the claude dir is `$CLAUDE_CONFIG_DIR` or `~/.claude` and the folder is encoded by replacing every character other than ASCII letters and digits with `-` (long names are cut at 200 characters plus a hash, so dirs are matched by prefix). A repo's chats are those whose recorded cwd is the repo folder or one of Claude Code's worktrees in it (`<repo>/.claude/worktrees/<name>`); chats in subfolders are not listed. harness only reads these files.
- **What is listed:** chats harness does not own: not the provider session of any harness session (archived and closed included), and not in harness's own worktrees (`harness-*`). A chat of a deleted in-place harness session shows up again as a Claude Code chat, since Claude Code still has it (since the automated filter below, only with "Show automated chats" on, because harness runs Claude Code as `sdk-py`). Title: the chat's custom title, else its generated title, else an older summary line, else the first prompt shortened with the D022 title rules. Message count: user prompts plus assistant replies with text. Last activity: the transcript file's change time.
- **Parsing:** harness parses the JSONL itself, defensively, rather than through the SDK's `list_sessions`/`get_session_messages`: those read the global config dir (not injectable in tests), shell out to git, and give no message count. The history follows the current branch from the newest message back through its parents (rewound branches are left out) and through compaction boundaries (`logicalParentUuid`), and skips meta, sidechain and compact-summary entries and Claude Code's own text (command output, hook context, notifications); slash commands show as `/name args`. Messages become the same events as harness sessions (`session.user_message`, `session.message` with text, thinking, tool use and tool result blocks).
- **Refresh:** a poll every 10 seconds, and every list request, rescans the dirs; only files whose time or size changed are parsed again. When a repo's list changes (new or updated chat, adoption, opened or closed in Claude Code), an ephemeral global `claude_chats.updated` event names the repos and clients list again. A chat being written is parsed again on each poll; the first scan of CV page's 72 chats (96 MB, one of 46 MB) took about 0.2 s, a rescan without changes about 2 ms.
- **Adopt:** `POST /api/claude-chats/{id}/adopt` creates an idle in-place session in the chat's original cwd (the repo folder or the Claude Code worktree), bound to the chat's session id, with the agent defaults, `base_ref` at that folder's HEAD and the history copied into its events. The next message resumes the chat through the SDK. harness never removes that folder: no worktree is recorded for it. Adopting an already adopted chat returns the existing session.
- **Live-elsewhere guard:** running Claude Code processes write `<claude dir>/sessions/<pid>.json` (`pid`, `sessionId`, `entrypoint`). Before every message to any session with a provider session id, harness refuses with 409 (`code: "open_in_claude_code"`, "This chat is open in Claude Code right now. Close it there first.") when such a file names the session and its pid is alive, unless it is harness's own SDK run (entrypoint `sdk-py` while harness holds the session's run). Two writers would interleave one transcript. Refined by D064 (PL-10): an idle Claude app process does not count.
- **Worktree location:** new harness worktrees go to `<repo>/.claude/worktrees/harness-<first 8 characters of the session id>` (branch names unchanged), so Claude Code sees them as the project's worktrees. Before creating one, harness adds `/.claude/worktrees/` to the repo's local exclude file (`git rev-parse --git-path info/exclude`) unless that line is already there. Worktrees created earlier in the data dir keep working. Removal deletes leftovers only inside `<repo>/.claude/worktrees/harness-*` or the data dir's worktrees folder, never Claude Code's own worktrees or other paths.
- **Limitation:** the Claude desktop app's sidebar lists only chats the app started itself; there is no supported way to add harness chats to it. They are reachable with `claude --resume` in the project folder.
- **Automated chats (follow-up):** each chat records its entrypoint, the first `entrypoint` field in its transcript (`cli` for Terminal, `claude-desktop` for the desktop app, `sdk-py` for a program using the Python Agent SDK). Chats whose entrypoint starts with `sdk` are `automated` and left out of `GET /api/claude-chats` unless `include_automated=true`; every chat carries `entrypoint` and `automated`, and one is still reachable by id. Reason: CV page had 72 chats, 70 of them automated security reviews (`sdk-py`); the user's own were `claude-desktop`. The PWA's "Show automated chats" switch is remembered per device (local storage) and lists them again with the flag.

## D029 (2026-10-06): Background subagents and commands (B22)

- **Findings (SDK and bundled CLI):** the `Agent` tool with `run_in_background: true` returns its tool result at once. The real lifecycle comes as system messages: `task_started` (`task_id`, `tool_use_id` of the Agent or Bash call, `task_type` such as `local_agent` or `local_bash`, `is_backgrounded`), `task_updated` (a `patch` with `is_backgrounded` when a foreground task moves to the background, or a terminal `status`: `completed`, `failed`, `killed`) and `task_notification` (`status`: `completed`, `failed`, `stopped`). A terminal state can arrive through either of the last two.
- **Decision:** the provider reports each as an `AgentTask` (`started`, `backgrounded`, `finished`), stored as the session event `session.agent_task`, also between turns, without starting a turn. Tasks still running when the agent process ends (close, crash, daemon stop) are reported finished as `stopped`.
- **Tracking:** a subagent started with `run_in_background`, or whose task starts or moves to the background, stays `running` after its tool result and after the main turn ends idle; its task finishing sets `done` (completed) or `failed` (failed or stopped). A tool result that is an error still fails it. Foreground subagents still end with their tool result. Bash calls with `run_in_background` (or moved there) are tracked as background commands named by the command's first line. ## D034 (2026-10-07): Pull request status, merge approval and summaries (B12)

- **Reading GitHub:** the daemon reads each pull request it opened with `gh pr view <url> --json state,mergeable,mergeStateStatus,statusCheckRollup,reviewDecision,headRefOid,url,number,title,createdAt`, through the user's own `gh` login and the injectable command runner, from the data directory (outside any checkout). `statusCheckRollup` holds both check runs and commit statuses, so `gh pr checks` is not needed. A check is `pending` until it completes, `success`, `skipped` (neutral or skipped, counted as passed) or `failure` (anything else, cancelled and timed out included). The checks state is `failure` if any failed, else `pending` if any run, else `success`, or `none` without checks.
- **Schedule:** a check every 15 s reads each open pull request whose interval passed: 60 s, or 5 min once nothing changed for an hour (measured from the last change harness saw, so new commits bring back the fast interval). Merged and closed ones are not read again. A failed read is logged at warning with the error kind only and waits for the next interval. An approve that pushes to a session with a pull request (a new one, or new commits) asks for a read at the next check.
- **Stored status:** the session's `pr` is `{number, url, title, state: open|merged|closed, checks: {state, passed, failed, pending, items: [{name, state, url}]}, mergeable (null while GitHub computes it), merge_state, review_decision, head_sha, created_at, changed_at, updated_at}`. Storing it does not change the session's `updated_at`, so polling never reorders the chat list. A change publishes the stored event `session.pr` `{pr}`; an unchanged read only moves `updated_at`.
- **Notices:** checks turning to failure (once per head commit) notify with the new kind `ci_failed` ("CI failed: a, b"); a merge approval notifies with `ready_to_merge`. Both are off for push by default, because the user wants the phone to ring only for permissions and choices; the inbox shows them regardless.
- **Merge approval:** the new approval kind `merge` (payload `{number, title, url, head_sha, checks: {state, passed, failed, pending}}`) is created when the pull request becomes ready: open, checks `success` or `none`, GitHub reports it mergeable, and its merge state is not blocked, dirty or draft. It is created once per head commit, so a dismissed one stays dismissed until something changes. It expires when the pull request is known not to be mergeable any more (new commits running checks, failures, conflicts, merged or closed on GitHub); a mergeable state GitHub is still computing keeps it. The approvals route only dismisses it (`{"dismiss": true}`).
- **Merge:** `POST /api/sessions/{id}/merge {method: squash|merge|rebase (default squash), delete_branch (default true)}` runs `gh pr merge <url> --repo <owner/name> --<method> [--delete-branch] --match-head-commit <sha>` with the daemon's credentials, so only the commit the checks ran on is merged. With `--repo` and outside a checkout gh deletes only the remote branch; the worktree removal deletes the local one (gh cannot switch a worktree's branch to main). Then it resolves the merge approval (`{action: "merged", method}`), publishes `pr.merged` `{url, method}`, reads the status again (falling back to marking it merged when GitHub cannot be read), and closes the session removing its worktree and branch. A gh failure publishes `git.failed` (step `merge`) and returns 502 with `step` and `stderr`, changing nothing. A worktree that cannot be removed after a successful merge leaves the session open to close again. Merging needs the session idle (409 while the agent works) and an open pull request (409 otherwise). The git guard still blocks `gh pr merge` for agents (D004).
- **External merges:** a pull request merged or closed on GitHub stops being read and expires its merge approval; the session stays open for the user to close, since it may hold later work.
- **Summaries:** when harness opens a pull request it stores `pr_summary`: up to two lines of the pending review's summary text (the agent's final summary; leading markdown removed, each line cut to 120 characters), then "N files changed, +A -D" from the whole work's diff. No model call. `GET /api/prs?repo=&state=` lists the pull requests harness opened with their summary and status, newest first; one not read yet counts as open.
- **PWA:** the chat header shows a chip with the pull request number and a dot (amber running, green passed, red failed, hollow without checks or before the first read, grey once merged or closed) that opens GitHub. The inbox shows merge approvals with **Merge (squash)** and **Open on GitHub** (also inline in the chat), and a "Checks failed" card with the failing check names and **Send to agent**, which sends "CI failed: <names>. Please fix." as a message into the session (since B31 followed by "You can't use gh or reach GitHub from here, so work from the code and the check names, and ask me for the logs if you need them.", on both clients, because agents have no GitHub login). That card shows while the pull request is open with failed checks, the chat is not working, closed or archived, and no review of new work is waiting. Superseded in part by D063: Send to agent sends the failing jobs' logs (`ci-feedback`).

## D035 (2026-10-07): Searchable history and replay (B13)

- **Index:** an SQLite FTS5 table (`search_index`, tokenizer `unicode61` with diacritics removed) holds one row per indexed piece: a session's title (kind `title`, replaced on rename), a user message (`user`), the main agent's text of one message (`assistant`, up to 20,000 characters), its tool calls as "Name argument" with the same short argument the activity lines use (`tool`), and the first 500 characters of tool results, whitespace collapsed (`tool_result`). Thinking and subagent messages are left out, because the transcript does not show them, so a hit there could not be opened. Claude Code chats harness does not own are indexed by title only (`claude_chat`, automated ones left out), from the chat list the daemon already scans every 10 s; a chat that leaves the list (adopted, deleted) leaves the index, and an adopted chat's history is indexed as its new session's events.
- **Maintenance:** the indexer reads the events table after a stored cursor (`search_state`), 200 events per transaction, yielding between batches, so the first pass over an existing database (cursor 0 after the migration) never holds the database long or blocks the event loop. It runs every 5 s, and every search first indexes what was stored since, once the first pass is done. Purging a session deletes its rows when its `session.deleted` event is indexed; searches join the sessions table, so a deleted session never shows in between.
- **Query:** `GET /api/search?q=&repo=&limit=` quotes every word, so FTS syntax (AND, OR, NOT, NEAR, column filters, parentheses) is searched as text and cannot fail; `"…"` keeps a phrase, a trailing `*` makes a prefix term, at most 16 terms. Ranking is bm25, then newest. Snippets mark matches with `[[` and `]]` and cut text with "…". The response is `{hits, indexing}`, where `indexing` is true until the first pass finished.
- **Replay:** `GET /api/sessions/{id}/events` takes `before` and `limit` besides `after`: events with `after < id < before`, oldest first; with `limit`, the ones nearest `before` when it is set, else nearest `after`. Without `limit` it returns everything as before.
- **PWA:** a search field at the top of the Projects tab; while it has text, results replace the project lists, grouped by chat (header with the highlighted title and the project, then each message hit with its kind). Tapping a hit opens the chat scrolled to that event's message, which glows briefly; a tool result hit lands on the message shown just before it (its tool call). Claude Code chat hits open the read-only view.

## D036 (2026-10-07): Stuck detection (B14)

- **Watcher:** a module follows every event live (ephemeral text deltas included) and, for each turn in progress (from a `running` or `waiting` state to any other state), tracks when it started, the last activity (messages, deltas, tool results, task updates, prompts), pending prompts (permission, question and plan approvals) and the latest tool call of the main agent and of each subagent with a count of identical repeats (same tool, same input with sorted keys). ## D049 (2026-10-07): The git guard reads commands like a shell, for every tool (B30)

- **Refines:** D013 layers 1 and 2 and the matching rules of D016.
- **Problem:** the guard was a regular expression over the Bash command. Quoted values (`git -C "my dir" commit`, `git -c user.name="A B" commit`), a quoted `"git"`, `gh -R o/r pr create` and many other forms slipped through, and the hook ran for the Bash tool only, while plugins (Serena's `execute_shell_command`), the CLI's Monitor tool and MCP servers (GitHub) can run commands or write to GitHub too.
- **Matching (`providers/git_commands.py`):** `shlex` splits the line with quotes and escapes resolved, line continuations joined, newlines and backticks treated as separators, and `#` not treated as a comment. Every word named `git` or `gh` (any path, any case, since the Mac's file system ignores case), and the dashed `git-commit`, `git-push` and friends, is checked from there, so prefixes and wrappers (`FOO=1`, `env`, `command`, `exec`, `xargs`, `timeout`, `nohup`, `sudo`, groups and subshells) need no special case. git's global options are stepped over with their values (`-C`, `-c`, `--git-dir`, `--work-tree`, `--namespace`, `--config-env`, `--opt=value`); denied subcommands are `commit`, `commit-tree`, `push`, `send-pack`, `http-push`, `subtree push`, and `config alias.* ...` that defines a commit or push alias. `-c alias.x=...` and `--config-env alias.x=...` aliases are expanded (an unknown `--config-env` value is denied). gh is denied for `pr create|new|merge` with flags and their values anywhere before the action (`gh -R o/r pr create`, `gh pr --repo o/r merge`).
- **Uncertain means denied:** a word that holds a command line of its own (`sh -c "..."`, `eval`, `env -S`, `python -c`, heredocs, `-c 'alias.x=!...'`) is read again, and there a mere mention of git and a write subcommand (or gh, pr and create or merge) denies; a line that cannot be parsed (unbalanced quotes) is denied on such a mention; a line that builds words at run time (`$`, backticks) is denied when it names commit or push (or pr with create or merge); git with an unknown global option is denied when any following word is a write subcommand.
- **Every tool:** the PreToolUse hook now matches `*`. It denies a tool whose input has a `command`, `cmd`, `script`, `shell_command` or `command_line` string (or argv list), or an `args`/`argv` list, that the matcher flags, and an MCP tool whose own name opens or merges a pull request, pushes or commits (`create_pull_request`, `merge_pull_request`, `push_files`, `create_or_update_file`, `git_commit`, `git_push`, `create_commit`, in any spelling). Other tools pass, even when their text mentions git (Edit, Write, Skill). The `Bash(...)` deny rules of layer 1 stay as they are.
- **Accepted false positives:** text that only mentions a blocked command (`echo "git push"`, `grep "git push" docs`), `$` lines that name commit or push for something else (`docker push $IMAGE`), and `gh pr` flags followed by a value that reads `create`. Read-only commands such as `git log --grep commit`, `git stash push`, `git -c alias.st=status st` and quoted paths stay allowed (a table of about 110 denied and 70 allowed cases in `tests/test_git_guard.py`).
- **Known misses (layers 3 and 4 remain the backstop):** aliases from the user's git config (`git ci`), commands encoded beyond plain text (`$'\x67it'`, base64 piped to `sh`), scripts the agent writes and runs later, and MCP tools whose names do not say what they do. The GitHub MCP server (unauthenticated today) could still write through such tools once the user authenticates it; the agent's gh has no token (layer 3).

## D050 (2026-10-07): The approved commit and push run nothing the agent could plant (B30)

- **Problem:** approving ran `git add`, `git commit`, `git push -u origin` and `gh pr create` in the agent's tree with the daemon's environment (credential helper, gh login, ssh agent). The agent can write `.git/hooks`, `core.hooksPath`, `filter.*` with `.gitattributes`, `core.fsmonitor`, `core.sshCommand`, `credential.helper`, `url.*.insteadOf` or a new origin URL, so one click could run its code with the user's credentials or send the work elsewhere. The review diff (after every turn, and on approval) had the same exposure through filters, textconv and fsmonitor.
- **Every daemon git command of the approve flow** (`gitops/safety.py`, `review/publish.py`) runs as `git -c core.hooksPath=/dev/null -c core.fsmonitor=false -c protocol.ext.allow=never ...`; commit and push also pass `--no-verify`, and push passes `--recurse-submodules=no`. `-c` settings are read after every config file, so they win over the repository's. Hooks therefore no longer run on approval, the user's own pre-commit hooks included (they used to be able to stop the commit).
- **Repository settings are checked, not trusted:** before anything is staged, `git config --list --show-scope` is read, and settings of the `local` and `worktree` scopes (with the files they include) that run a program or send data elsewhere stop publishing with 409 `code: "unsafe_repo_config"` and the list of keys: `core.sshCommand`, `core.gitProxy`, `core.askPass`, `core.alternateRefsCommand`, a non-boolean `core.fsmonitor`, `ssh.variant`, `credential.*`, `url.*.insteadOf` and `pushInsteadOf`, `http.*` (except `postBuffer`, `lowSpeedLimit`, `lowSpeedTime`, `version`, `maxRequests`), `remote.*.receivepack`, `uploadpack`, `proxy` and `vcs`, `filter.*` (except `required` and the exact values `git lfs install --local` writes), `gpg.*`, `hook.*` and `protocol.*` (except `protocol.version`). Refusing is chosen over switching them off for publishing, since a filter switched off would commit different content. System and global config are the user's own and stay in effect (so `GIT_CONFIG_NOSYSTEM` is not used: it would drop the user's osxkeychain credential helper).
- **Diffs** run with the same overrides plus `--no-textconv` and `--no-ext-diff`, and with each filter driver of the repository's own config switched off (`-c filter.<name>.clean=` and so on); a driver name that `-c` cannot express (it contains `=`) fails the diff instead.
- **Push only to a confirmed URL:** each repo's config gains `remote_url`, origin's single push URL (after git's own rewriting, with http credentials left out) recorded at registration, before any agent ran there; a folder that becomes a repository, or a repo without exactly one push URL, has none. Approving again with `confirm_remote_url` set to origin's current URL pushes there and records it; the user can also set `remote_url` in `~/.config/harness/repos/<name>.toml`. `gh pr create` gets `--repo owner/name` from that URL when it is on github.com, so gh does not pick another remote.
- **Left open:** agent processes still running in the background at approval time could change the config between the check and the push; other daemon git commands outside the approve flow and the review diff (worktree creation and removal, the ref audit, file listing) still run with the repository's hooks and config; and the Mac app and the PWA do not yet offer the confirm step (the 409 detail tells the user what to do). Superseded in part: the other git commands run hardened (D064) and both clients offer the confirm step (D063).
- **Corrected by D068 (B34):** diffs and the dirty-file listing no longer look inside submodules and nested repositories (`--ignore-submodules=dirty`), staging also switches off the filters their own configs name, a file is binary only by its content, and git-lfs repositories are refused at approve.
- **Follow-up (2026-10-07, automated security review):** the refused settings now also cover `diff.external`, `diff.*.command`, `diff.*.textconv`, `merge.*.driver`, `core.editor`, `sequence.editor`, `core.pager`, `pager.*` and `interactive.diffFilter`, and the name-status diff also runs with `--no-ext-diff --no-textconv`.

## D053 (2026-10-08): Approved pushes name their branch, and refs are checked again before publishing (B31)

## D075 (2026-10-14): The Mac app asks the daemon for its token over a private socket (B38)

- **Problem:** the Mac app read its device token from the login Keychain item the daemon writes (service `harness`, account `local-device-token`). The item's partition list gets one `cdhash:` entry per build, since the free self-signed certificate of D042 has no team ID, so every new build asked for the login keychain password, and "Allow" (rather than "Always Allow") asked again at every launch.
- **Decision (user, 2026-10-14, from three options):** the daemon hands the token to the Mac app over a Unix socket, `token.sock` in its data folder (`~/Library/Application Support/harness/token.sock`). The token stays in the daemon's Keychain item, which the app no longer reads.
- **Daemon (`harness.auth.token_socket`):** started with the app's lifespan, after the local device is ensured, and stopped first on shutdown. On start it makes the folder 0700, removes a stale socket or file at the path (one nobody answers on, as a killed daemon leaves), refuses to start when another daemon answers there, listens, and makes the socket 0600. On stop it removes the socket only if it is still the one it made. For each connection it reads the peer's credentials (`LOCAL_PEERCRED` on macOS, `SO_PEERCRED` on Linux, where the CI runs), closes without an answer unless the peer's effective uid is the daemon's own, then writes the token and a newline and closes. It never reads what a client sends and never logs the token. Each answer comes from `ensure_local_device()`, one at a time, so a revoked local device gets a new token on the next ask. Paths built in tests serve no socket (`AppPaths.token_socket` is None unless set); Unix socket paths are limited to about 104 bytes, so a very long `HARNESS_DATA_DIR` stops the daemon from starting.
- **Mac (`SocketTokenStore` in HarnessKit):** it connects to the socket in the default data folder (a daemon run with `HARNESS_DATA_DIR` elsewhere is not found) and reads until the daemon closes, with a 5 second timeout. No socket file, or a socket nobody listens on, means the daemon is not running: the app opens without a token and shows the daemon as unreachable, with Start harness service, instead of the former "not set up" screen. A connection closed without a token, an answer that is not a URL-safe token (or is over 4096 bytes) and other socket errors are errors. The app asks again on connect (Retry, Start harness service) when it has no token yet or the daemon refused the one in use, and when the event stream is refused (close 4401) it asks once more and reconnects at once if the token changed: the daemon started after the app, or made a new token. `KeychainTokenStore` is removed.
- **Trade-off accepted by the user:** any process running as the user can ask for the token. Other users cannot open the folder or the socket, and the uid check refuses them as well.

## D087 (2026-10-15): Messages go into the running turn; rewind the conversation and fork like Claude Code (B59, wave 2)

- **Why:** a message sent while Claude worked waited for the turn's end (D032), and only files could be rewound (IMP-02). - **Steering:** a message sent while a turn runs on an open run is written into the running Claude Code process at once (`query` with a uuid). Claude Code reads it at its next step (after a tool result), echoes it under that uuid, and the turn goes on to one result; the message shows in the transcript where it was read. Until then it is a pending message: stored in Nest's queue marked `sent`. When the turn ends, Nest takes back what Claude Code did not read (the CLI's `cancel_async_message` control request, which the SDK has no method for) and sends it as the next turn as before, so the session never rests in between and the new turn is a message turn (B56's start of work is noted). When Claude Code says it had already read it, the session stays running and its echo starts the next turn. After a Stop or a failure such a message went with the turn and waits again. A turn Claude Code ends with `error_during_execution` and `[ede_diagnostic] result_type=user` while it holds messages written into it is no failure: the messages start the next turn at once, and its result, like that of a turn Send now stopped, carries `handoff: true`; the result of a turn the user stopped carries `stopped: true`; clients show no error for either, only the turn's usual end line. - **Send now and remove:** `POST /api/sessions/{id}/queue/{message_id}/send-now` puts the message first and stops the turn, as a nudge does (D036); messages Claude Code has not read are taken back first so they do not run before it; on a resting chat it starts the message at once. Removing a pending message takes it back from Claude Code first; once read it cannot be removed (409 `message_taken`). Editing is removing and sending again. Stop takes back unread messages before interrupting, so they wait instead of running after the Stop.
- **Still queued as before:** no open run, a provider that cannot steer, a Stop or Send now in progress, publishing, a files restore, a message with a new file attachment (its folder needs a new run), another effort or set of subagents, a pixie chat due for a fresh run, and messages behind one that waits (order is kept).
