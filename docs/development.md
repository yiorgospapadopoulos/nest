# Working on Nest

For working on Nest itself. To use it, see the [README](../README.md) and [Using Nest](using-nest.md).

## Layout

| Path | What |
|---|---|
| `daemon/` | Python daemon (FastAPI, websockets, Claude Agent SDK, Codex app-server, SQLite). Runs on the Mac as a background service. |
| `web/` | The web app (React, TypeScript, Vite), served by the daemon: the iPhone PWA, the Linux app's interface and the Mac app's chat panes. |
| `apple/` | Native Mac app: a Swift package with the `NestKit` logic library and the `NestApp` SwiftUI executable; its chat transcripts are the web chat in web views. |
| `desktop/` | Linux desktop app (Tauri 2, Rust) around the web UI's desktop layout (`web/desktop.html`), built in Docker. |
| `design/` | `tokens.toml`, the design tokens shared by both clients (`make tokens` regenerates the CSS and Swift outputs). Both clients use the `[colors.mac]` palette and lane colours; the Mac also its `mac_*` radii and spacing (Swift `DesignTokens.Colors.Mac`), the iPhone its `phone_*` type sizes, row height and card radius (CSS `--typography-size-phone-*`, `--spacing-phone-row`, `--radius-phone-card`). The iPhone no longer offers glass themes or wallpapers; their token tables are still generated but unused. |

## Prerequisites

- macOS with [uv](https://docs.astral.sh/uv/) and Python 3.12
- Node.js with npm
- Claude Code, logged in with your subscription
- Optional, for Codex chats: a Codex login with a ChatGPT plan (Settings > Accounts > Codex > Sign in on the Mac, or `codex login`). The Codex binary comes with the daemon's dependencies (`openai-codex-cli-bin`), so nothing else is installed.
- Optional, for the other engines (OpenCode, Gemini CLI, Copilot CLI, Grok Build): nothing to install; `make install` fetches the versions Nest lists with npm (see More engines). Antigravity is downloaded on first use. Cursor agent is the exception: Nest does not fetch it, so it needs your own install of Cursor's CLI (`agent`). `nestd engines registry` shows where the ACP Registry lists newer versions than Nest pins
- Xcode 27 or later (Mac app), Tailscale (iPhone access), the `gh` CLI logged in (pull requests)

## Development

```bash
make install   # install daemon and web dependencies
make check     # every quality gate: format, lint and types of every part first, then tests and builds, then audits
make check-changed  # the gates of only the parts changed since the merge base with main (BASE=origin/main to change it)
make fmt       # auto-format and auto-fix lint
make test      # tests only (and the web and Mac builds)
make coverage  # the coverage report of every part (not part of the gates)
make check-apple  # Swift lint, then one build of the app and its tests, then the tests
make app       # build apple/build/Nest.app (signed with "Nest Local Signing" when present, else ad hoc)
make run-app   # build and open the Mac app
make install-app  # build and copy Nest.app into /Applications
make tokens    # regenerate design token outputs
make icon      # render the app icon PNGs from the icon pixie's sprite and build AppIcon.icns
```

The daemon tests in `make check`, `make check-daemon` and `make test` run in 4 parallel worker processes (pytest-xdist) by default; `PYTEST_WORKERS=auto make check` uses one per core and `PYTEST_WORKERS=0` runs one process. The gates run without coverage; `make coverage` merges the workers' coverage into one report. A targeted run such as `cd daemon && uv run pytest tests/test_cli.py` stays single-process unless `-n` is given.

`make check-changed` asks `nestd gates changed` which parts the work touched since the merge base with `BASE` (default `main`), counting committed, staged, unstaged and untracked files, prints why, and runs only those gates in `make check`'s order (the lint stage of each part, then the tests, then the audits). A file in `daemon/`, `web/` or `apple/` runs that part; `design/` and the generator in `daemon/src/nestd/design/` run all three; the generated token and icon files run their part and the daemon, whose tests check them; `README.md`, `LICENSE` and `docs/` run nothing; anything else (the `Makefile`, `.github/`, a new top-level folder) runs everything, as does a failure to work the parts out. It is the gate for work in a worktree; the full `make check` runs before merging into `main` and after cross-cutting changes.

### CI

CI: `.github/workflows/check.yml` is set to run `make check-daemon` and `make check-web` on GitHub Actions (`ubuntu-latest`) for every push and pull request. Off `main`, a first job runs `nestd gates changed` against `origin/main` (or the pull request's base) and each job runs only when its part changed, by the same rules; on `main` both always run. The Swift gates run only locally (`make check-apple`).

### Tests

Tests cover what matters (core behaviour, risky logic, important failure paths and every fixed bug), not a coverage number. `make coverage` prints each part's coverage; no gate measures or fails on a percentage.

Tests stay fast and deterministic: they wait for an event or a signal from a fake, never for a wall-clock deadline or a real sleep. Daemon API tests start the background loops only when a test is about one; daemon tests copy a migrated template database and template repositories, and chats work in place unless a test is about worktrees.

## Releases

`VERSION` holds the one version; `make version` writes it to every part, and a test fails if any differs. `make release` builds everything of a release into the gitignored `release/out/<version>/` on a Mac: the daemon wheel with the web app inside, its pinned requirements with hashes, the signed and notarized Mac app, the Linux AppImage and `.deb` for x86_64 and arm64 in Docker, `install.sh`, and `latest.json` with its signature. It stops if `release/notes/<version>.md` or the release key is missing, and, when it builds the Mac app, if the Developer ID certificate or the notary profile is missing (see [How the Mac app is signed](#how-the-mac-app-is-signed)). It also stops on uncommitted changes: any change to a tracked file, or a new file in `daemon/`, `web/`, `apple/`, `desktop/`, `design/` or `release/`, since what it builds is signed and shipped and the public repository gets the committed files only. `latest.json` records the commit it was built from. For a test build only, `NEST_RELEASE_ALLOW_DIRTY=1 make release` builds anyway and marks `latest.json` with `"dirty": true`. `NEST_RELEASE_PARTS` builds some of it. It publishes nothing. `install.sh` and the daemon read `NEST_RELEASE_URL`, so a test release can be served from a local address. On a computer with no Nest yet, `install.sh` installs the newest Claude Code and Codex in place of the pinned ones: `python -m nestd.updates.first_install` (standard library only) names the newer ones and writes the requirements without them, those go in with their hashes, the newest engines as built wheels, and `nestd engines selfcheck` decides; any failure starts over on the pinned requirements.

### How releases are signed

`latest.json` lists each file of a release with its sha256, and `latest.json.sig` beside it is its signature by Nest's release key. `install.sh` and the daemon's updater check that signature before they read anything in `latest.json`, then check every download against its sha256, so a release whose list or files were changed after it was signed installs nothing. The install line's own first download of `install.sh` is trusted through HTTPS, as with any install line: from the project's GitHub Pages site, where `.github/workflows/pages.yml` copies the latest release's own `install.sh` unchanged each time a release is published, or from the release address for a release served elsewhere; no file of the release it downloads after that is trusted without the signature. The engines are the one exception: on a first install the newest Claude Code and Codex come from PyPI as built wheels over HTTPS, without the release's hash pins, and are kept only if `nestd engines selfcheck` passes in the new install. Engine updates after that work the same way, the npm engines coming from npm. `install.sh` stops with "This release isn't signed by Nest's release key" or "This release has no signature"; the updater logs the same and offers no update.

The key is ECDSA P-256 with SHA-256, because macOS's own `openssl` (LibreSSL) cannot check Ed25519 and `install.sh` must run on a clean Mac with no Python. The private key lives only in the release Mac's login Keychain, as the password item "Nest release key" whose account is the key's fingerprint. It is never written to a file. The public keys are `RELEASE_KEYS` in `daemon/src/nestd/updates/signature.py` and in `release/install.sh`, and a test checks that the two match. `make_manifest.py` signs `latest.json` at the end of `make release` with the private key of the first of them, and `make release` stops at the start if this Keychain cannot sign.

The item trusts no app, so macOS asks every time the key is read: once for the check at the start of `make release` and once for signing at the end, and for `export` and `lock`. Each time, type your login password and click Allow. Never click Always Allow: it trusts the Python every script and agent on this Mac shares, and any of them could then read the key and sign a release. A key stored before this rule trusted that Python; run `release_key.py lock` once to save it again with no app trusted.

`release/release_key.py` (run from `daemon/` with `uv run python ../release/release_key.py`):

| Command | Does |
|---|---|
| `new` | Makes a key in the Keychain and prints its public key. Run once per key. |
| `public` | Prints `RELEASE_KEYS` and which of them this Keychain holds. |
| `check` | Stops unless this Keychain can sign a release. |
| `export` | Copies the signing key to the clipboard as one line, for a backup. |
| `import` | Puts a trusted key from the clipboard into this Keychain, then clears the clipboard. |
| `check-backup` | Says whether the clipboard holds a key Nest trusts, then clears it. Stores nothing. |
| `lock` | Saves the stored key again so that it trusts no app and every read asks. Run once on a key stored before this rule. |

### Backing up the release key

Without a copy, losing this Mac means changing the key, and every installed Nest then refuses updates until its user runs the install line again. So keep a backup in a password manager, such as Apple's Passwords app:

1. Run `release_key.py export`. The key goes to the clipboard as one line of about 180 characters, never to the screen.
2. Paste it into the password field of a new entry, "Nest release key".
3. Copy it back from that entry and run `release_key.py check-backup`, which checks it is the key Nest trusts and clears the clipboard.

On a new Mac, copy the password from that entry and run `release_key.py import`; `make release` then works there as before. If you use a clipboard history app, clear it afterwards.

### Changing the release key

A release is accepted if any one of `RELEASE_KEYS` signed it, and it is signed with the first. To change the key while users keep updating:

1. Run `release_key.py new` and add its public key to `RELEASE_KEYS` in both files, after the current one.
2. Publish at least one release that way. It is still signed with the old key, so every installed Nest accepts it, and it teaches them the new key.
3. Move the new key first and remove the old one from both files. Releases from then on are signed with the new key. Delete the old Keychain item once no release needs it.

A Nest that skipped every release of step 2 refuses the later ones as unsigned; running the install line again fixes it, as the line takes the latest release's `install.sh`, which carries the new key.

If the key may have leaked, skip step 2: put only the new key in `RELEASE_KEYS` and publish at once. Every installed Nest then refuses the update, which is right, as it cannot tell the real one from a forged one. Say so in the release notes and on the project page: users update by running the install line again.

### How the Mac app is signed

A release's Nest.app is signed with the team's Developer ID Application certificate (team `Y46V894D78`), notarized by Apple and stapled, so it opens with no warning however it was downloaded, and offline too. `make release` signs the Nest Computer helper and then the app with the hardened runtime and a secure timestamp, checks the signature and its team, sends a zip of the app to Apple with `xcrun notarytool submit --wait --keychain-profile nest-notary`, staples the ticket to the app, checks that Gatekeeper accepts it (`spctl`), and only then zips it for the release. A rejected submission stops the build and prints Apple's log. A ticket cannot be stapled to a zip, which is why the stapled app is zipped after.

The certificate and the notary profile live only in the release Mac's login Keychain. To set them up on a new Mac: create a Developer ID Application certificate on the Apple Developer website (the account holder only), install it with the Developer ID G2 intermediate certificate, then run `xcrun notarytool store-credentials nest-notary` with an app-specific password from your Apple Account. The certificate needs no backup: a lost one is replaced on the website, and as macOS ties an app's permissions to its team, users see nothing. Renew it before it runs out (2027-12-09); releases signed before then keep working. Keep only one valid copy in the keychain, as `codesign` refuses a name two certificates share.

The app's only entitlement is the microphone, for dictation (`apple/support/Nest.entitlements`). The helper has none.

## The Mac app

The app icon is the nightshade pixie in the standard violet on a black tile, the same in every appearance and icon style. `nestd design icon` (`make icon`) renders it from `design/mascots.toml` without an image library: `apple/support/AppIcon-1024.png` and the `.icns` built from it, the sprite alone for `apple/support/AppIcon.icon`, and the iPhone's `web/build/icons`. `make app` compiles the `.icon` bundle with `actool` into the app's `Assets.car`, which macOS 26 draws the Dock and Finder icon from; `actool` also writes flat images into it for macOS 15, the oldest the app runs on. The committed PNGs must match a fresh render (a daemon test checks), so run `make icon` after changing the sprite.

The Mac app gets its device token from the running daemon over a private socket, so it never asks for the login keychain password. When the daemon is not running, the window shows it as unreachable with Start Nest service, and the app asks for the token again once the daemon is up. `make app` signs the app with a self-signed code-signing certificate named `Nest Local Signing` when the login keychain has one (Certificate Assistant > Create a Certificate, Self-Signed Root, Code Signing, then Always Trust for Code Signing in Keychain Access), else with `Harness Local Signing`, the one made before the rename, and ad hoc otherwise. It needs no Apple account. Every build runs under the hardened runtime with the release's entitlements, so a developer build meets the same limits as a release.

For visual review, a debug build renders the window offscreen without showing it: `cd apple && swift build && "$(swift build --show-bin-path)/NestApp" --render-snapshots <folder>` (sample data) or `--render-live <folder>` (the local daemon, read-only).

## Running the daemon

```bash
cd daemon
uv run nestd serve              # run in the foreground on 127.0.0.1:8765
uv run nestd service install    # install and start the launchd background service
uv run nestd service status     # exit 0 when the service is loaded
uv run nestd service uninstall  # stop and remove it
uv run nestd pair               # print a one-time pairing code for a new device
```

- Config: `~/.config/nest/` (override with `NEST_CONFIG_DIR`). A default `settings.toml` is written on first run.
- Data and logs: `~/Library/Application Support/nest/` (override with `NEST_DATA_DIR`), with the database `nest.db`; the service logs to `logs/daemon.log` there, including what Claude Code writes to stderr (at debug level, credentials in URLs removed).
- The launchd service is `com.nest.daemon` (`~/Library/LaunchAgents/com.nest.daemon.plist`), running `daemon/.venv/bin/python3 -m nestd serve`; `serve` then switches to the Python of an engine environment in `environments/` in the data folder when one should run (after an engine update), with the same process id.
- On Linux: config in `$XDG_CONFIG_HOME/nest` (default `~/.config/nest`), data and logs in `$XDG_DATA_HOME/nest` (default `~/.local/share/nest`), `NEST_*` still overriding them. `nestd service install` writes the systemd user unit `~/.config/systemd/user/nest.service` (`Restart=always`, so Restart Nest works, and `KillMode=process`, so stopping the service leaves the terminals and editors Nest opened for you running) and runs `systemctl --user daemon-reload`, `enable` and `restart`; `status` and `uninstall` use `systemctl --user` too. To keep it running while you are logged out, run `loginctl enable-linger` yourself. Secrets go to the Secret Service through the keyring (gnome-keyring on Ubuntu); with no Secret Service or a locked keyring, `nestd serve` stops with one line saying what to do. Open in offers each code editor it finds (VS Code, Cursor, Zed, the JetBrains IDEs and Android Studio), looking for its command (such as `code`, `zed`, `pycharm` or `idea.sh`) on the PATH, then in JetBrains Toolbox's `~/.local/share/JetBrains/Toolbox/scripts`, `/snap/bin` and the flatpak export folders (`~/.local/share/flatpak/exports/bin`, `/var/lib/flatpak/exports/bin`); the file manager and a terminal use `xdg-open` and `x-terminal-emulator` (else `gnome-terminal`). The move from the old harness folders happens only on macOS.
- The daemon serves the built PWA from `web/dist` (override with `NEST_WEB_DIST`), and the Mac app's chat transcripts with it; run `cd web && npm run build` after changing it. Browser websocket connections must come from the same origin or from `server.allowed_origins` in `settings.toml`.
- The Mac's own device token lives in the macOS Keychain (service `nest`, account `local-device-token`). The daemon hands it to the Mac app over a Unix socket, `token.sock` in the data folder: the folder is 0700, the socket 0600, and a process running as another user is refused, and so are Nest's own agents and the commands they run (anything under the daemon, or in a session one of them began). Any other process running as you can ask for it. The Mac app looks in the default data folder, or in `NEST_DATA_DIR` when it is launched with that set; `NEST_DAEMON_URL` (an http or https loopback URL such as `http://127.0.0.1:8812`, anything else is ignored) points it at a test daemon instead of `127.0.0.1:8765`. Both are read once at launch.
- Outside clients (Settings > Terminal agents) get their tokens from a second socket, `outside.sock`, beside it: the client writes its kind (`claude_code`, `codex`, `other` or `shell`) on one line and gets one JSON line back, a fresh token or why not (`off`, `inside_nest`, `unknown_client`). A process whose parents reach the daemon, whose parent is launchd, or whose session leader runs under the daemon or is gone is refused, so Nest's own agents and the commands they run get none. Tokens live in memory only. The code is in `daemon/src/nestd/outside/`: `socket.py`, the service and store, `config.py` (adds `nest-app` with `claude mcp add` and `codex mcp add`), and the thin client the `nest` command (`command.py`) and `nest mcp` (`mcp_server.py`) share (`client.py`).

## A daemon on another machine

The Mac app can use a Nest daemon on another machine on the tailnet (a second Mac now, a Linux box later) instead of the one on this Mac, one at a time. That machine needs its own Nest install with the service running, its own `tailscale serve --bg 8765` (what Share with my devices runs; see iPhone in the [README](../README.md#iphone)), its own clones of the repos and its own `~/.config/nest` (nothing syncs between machines), and its own `claude`, `codex` and `gh` logins.

- **Token:** each remote's device token is a login Keychain item the app makes itself (service `nest`, account `remote-device-token <address>`), read without a prompt also by later builds signed with the same local identity. This Mac's daemon still hands its token over `token.sock`. `NEST_DAEMON_URL` and `NEST_DATA_DIR` stay a launch-time override for This Mac only (test daemons).
- `GET /api/health` answers `machine`, the daemon machine's name (macOS's computer name, else the host name without `.local`).

## Pixies and Nest's tools on other engines

Pixies and Nest's tools on Codex: a pixie runs on Claude unless its `provider` names another engine, such as `"codex"` (`POST/PATCH /api/pixies`, 422 for an unknown engine; moving a pixie to another engine resets its model and thinking unless given and archives its open chat, so its next message starts a chat on the new engine; a Codex pixie takes no Claude model default; its skill list switches every other skill off for its runs, through the thread's `skills.config`). Its chats and habit runs then run on Codex with the same guarded settings as on Claude (Codex asks Nest before every command it does not know to be read-only and every file change, with network and no extra sandbox; Nest declines git pushes and pull requests while pushing is off, and edits outside the pixie's write root) and its Nest tools. A Codex run gets the same Nest tools a Claude run gets (a pixie's memory, notes and soul, its habits and reports, its Nest actions, artifacts, calling pixies) from a local MCP server the daemon starts for that run only: streamable HTTP on `127.0.0.1` and a random port, `/pixie/mcp` and `/nest/mcp`, every request needing the run's random bearer token, stopped with the run (`nestd/providers/codex_tools.py`). Codex learns it from the thread's config overrides (`mcp_servers.<name>` with `bearer_token_env_var`), never from `~/.codex/config.toml`; the token is only in the app-server's environment. Pixie calls: a pixie works the same whichever engine it and its caller run on. Claude runs a called Claude pixie as its own subagent and Codex a called Codex pixie as its own (each pixie a role of the run's thread, `agents.<slug>` in the thread's config, with its prompt, model and effort in a role file Nest removes with the run). A call across engines, and any call from or to an ACP engine, goes through Nest's `call_pixie` tool, which runs the pixie as a session of its own in the caller's folder (`pixie_id` set, `called_by` naming the calling chat) and makes it behave like a subagent: `run_in_background` returns at once and the report comes back into the chat when it ends (written into a running turn, or starting a turn, shown as "@pixie finished"); calling the same pixie again continues its session unless the pixie changed or `fresh` is set; its work, activity, plan, tokens and Stop show on the caller's row; its approvals and questions show in the caller's Needs you; it works in its own mode, as set in its settings, Read only pixies cannot edit, git pushes and pull requests follow the push setting; at the usage limit it pauses, and a restart marks it interrupted. The same call rules hold (the main agent calls solo pixies and leaders, a leader its members). In guarded Codex runs Codex is told to ask before every tool of your own MCP servers, and Nest declines a call that `tool_writes` flags (a tool named like `create_pull_request`, or one whose input holds a git write command). Codex's approval request does not name the tool, so Nest takes the name from the tool call Codex started just before it asked. A Codex run's developer instructions name its Nest tools (`mcp__pixie__memory_read` and so on), so the model finds them among your own MCP tools. Commands show without Codex's shell wrapper (`ls`, not `/bin/zsh -lc ls`).

## Computer use

The daemon's `nestd/computer` package gives chats five tools (`computer_targets`, `computer_open`, `computer_view`, `computer_act`, `computer_release`) on every engine, through the same in-process and local MCP servers as Nest's other tools. They are in every chat's runs while Settings > Computer use (`[computer_use] enabled`) is on, and a chat asks the user the first time it uses each target; every call checks again, so switching off works at once. Each kind of target has a backend in `nestd/computer/backends/`: Mac apps (`mac:<bundle id>`), iOS Simulator devices (`ios:<udid>`, `xcrun simctl` plus Simulator.app's window), Android emulators (`android:<serial>`, `adb` and `emulator`) and the shared browser (`browser`, a Chrome-based browser with its own profile in `<data>/computer/browser`, driven over the DevTools protocol). `nestd/computer/safety.py` holds what is never done and what is asked first; `service.py` holds the approvals, one chat per target and the latest screenshot (`GET /api/sessions/{id}/computer/frame`).

Mac apps go through the helper app `Nest.app/Contents/Helpers/Nest Computer.app` (`apple/Sources/NestComputer`, bundle id `local.nest.computer`), which holds the Accessibility permission so the Python program agents' shells run never does. macOS checks Screen Recording for an app inside another app against the outer one, so window screenshots use Nest.app's Screen Recording. `make app` builds it and signs it with the same certificate as Nest.app, so macOS keeps its permissions across builds. The daemon starts it with `open` (so macOS counts it as its own app), finds Nest.app at `NEST_MAC_APP` or `/Applications/Nest.app`, and talks to it over a Unix socket at `<data>/computer/helper.sock` with JSON lines; the helper answers only the daemon's process and quits when the daemon does. Whoever launches the helper names that process, so at launch the helper asks launchd (`launchctl print gui/<uid>/com.nest.daemon`) for the service's running pid and quits unless it is the one named: another program cannot start its own helper and use its permission without replacing Nest's service. It uses public macOS APIs only: accessibility actions and menus, window-created notifications, keys sent to the app's process, and `screencapture -l` for window screenshots (ScreenCaptureKit failed on macOS 27.2). macOS lists only the windows on the current desktop, so the helper also keeps windows it saw before or saw being opened.

Known limit: the shared browser's DevTools port is on `127.0.0.1` and named in its profile folder, so another program running as you could drive that browser without Nest's cards.

A test copy needs its own Nest.app copy with the helper inside, `NEST_MAC_APP` pointing at it, Accessibility for its helper and Screen Recording for the copy itself. A test copy daemon started by hand is not the `com.nest.daemon` service, so its helper refuses to start and Mac apps and the iOS Simulator cannot be used from it; the Android emulator and the shared browser still work.

## Renamed from harness

Nest was called harness until October 2026. What it kept under the old name moves on its own, and nothing is deleted:

- **Folders.** When `nestd` starts (`serve`, `pair` or `service install`) and finds `~/.config/harness/` or `~/Library/Application Support/harness/` but not the Nest folder next to it, it copies the old folder (links stay links, permissions are kept, the database with its `-wal` and `-shm` files, renamed `nest.db`; the token socket is left out and made again), gives the copy the new name, renames the old folder to `harness.harness-backup` and puts a link at the old path to the new folder. Paths saved before the move (worktrees, attachments, pixie folders, git's worktree records, Claude Code's history for old chats) keep working through the link. A folder named by a variable is not moved. The move refuses to run while the old daemon still answers on its socket, or when a backup or a half-finished copy (`nest.moving`) is already there; then it says so in the log and the daemon exits, with the old folder untouched. A later start does nothing. Delete the `*.harness-backup` folders yourself once you are happy.
- **Variables.** `NEST_CONFIG_DIR`, `NEST_DATA_DIR` and `NEST_WEB_DIST` fall back to `HARNESS_CONFIG_DIR`, `HARNESS_DATA_DIR` and `HARNESS_WEB_DIST` when unset; a data folder named that way gets its `harness.db` renamed `nest.db`.
- **Service.** `nestd service install` stops and removes the old `com.harness.daemon` service before it moves the folders and installs `com.nest.daemon`.
- **Keychain.** A secret missing under the service `nest` is read from `harness` and written under `nest`; the old item stays.
- **Phone and worktrees.** A phone paired before keeps working: its `harness_token` cookie is still accepted. Worktrees made before (`<repo>/.claude/worktrees/harness-<id>`) are still Nest's own.
- **Mac app.** `make install-app` installs `/Applications/Nest.app` (bundle id `local.nest.app`) and removes `/Applications/Harness.app`. On its first launch Nest copies the old app's settings (`local.harness.app`, keeping any it already has, with background paths following) and its backgrounds folder (`~/Library/Application Support/local.harness.app/`, left in place). macOS asks again for microphone and speech recognition, which belong to the app's bundle id.
- **iPhone app.** Choices saved on the device (`harness.appearance`, `harness.drafts`, `harness.foldedTeams`, `harness.showAutomatedChats`) are moved to `nest.*` on the first start; the old offline cache is dropped. A Home Screen icon added before keeps its old name until it is added again.

## API overview

All routes need a device token (`Authorization: Bearer <token>` or the `nest_token` cookie; the `harness_token` cookie from before the rename is still accepted), except `GET /api/health` and `POST /api/pairing/redeem`, and the local model proxy under `/local/`, which takes the daemon's own key instead. Routes under `/api/outside` are the exception the other way: they take only an outside client's token, which no other route accepts. The event socket also takes the token as the WebSocket subprotocol pair `nest`, `nest.token.<token>` (a browser page cannot set headers there; only `nest` is echoed back). Pages from the desktop app (`tauri://localhost`, and `http://tauri.localhost` for a future Windows app) and from `server.allowed_origins` get CORS headers for the Authorization and Content-Type headers, without credentials; preflights need no token, and other origins get none.
